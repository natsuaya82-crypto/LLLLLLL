## 境目 ── 二本が違う答えを持っている所

**バグはここに出ます。**八つ見つけました。

### A. 読めない一本が、無事なサーバーを上書きする　【走らせて確認】

iPhone の中の一本が壊れて（JSON として読めなくなって）いると、
合わせる所は**壊れたほうを答えとして返します。**そのままサーバーへ送られ、
**サーバーの唯一の版が壊れたものになります。**

**走らせました。**`www/sync.js` と `www/net.js` の断る所を抜き出して
Node で動かし、四行が全部そのとおりになることを確認しています:

```
iPhone の単語 = 読めない文字列   サーバーの単語 = 3000 語
  → 合わせる所は「読めない文字列」を返す      ← 確認した
  → 縮む書き込みを断る所は通す（同じものなので比較にかからない） ← 確認した
  → サーバーの中身と違うので送信が飛ぶ         ← 確認した
  → サーバーの 3000 語が読めない文字列になる
```

**逆向きも同じです。**サーバーの側が壊れていれば iPhone の側が返り、
そちらは正しい動きです。**問題は「読めない＝無い」として扱っていることで、
CLAUDE.md が名指しで禁じている形です**（「『空』と『壊れている』は別の状態で、
枝を共有してはならない」）。

**ファイルの側は断ります。**壊れているものはファイルに書き出されません。
**サーバーには断る所がありません。**壊れているかを見分ける所（⑩）は、
同期の道では一度も呼ばれていません。

### B. 保存の失敗が、三十四か所のうち三十一か所で黙って済まされる　【数えて確認・押していない】

**数えました。**`www/` の全ファイルで iPhone に書き込む所は **34 か所**、
そのうち **31 か所が、失敗を何も言わずに飲みます。**

言うのは **1 か所だけ**です（投稿の保存。「いっぱいです」と出ます）。
残り 2 か所は、少なくとも印を立てるか、その場で止まります。

一番効くのが**言語の保存**で、ここが失敗すると
**単語も行も名前も書記体系も設定も索引も、一つも書かれず、画面には何も出ません。**
そのうえで**バックアップは先に走っているので、書けなかった古い中身が
ファイルに書き出されます。**

**押していません。**ストレージを満杯にした実機は触っていません。読んで数えました。

### C. 「無いものだけ埋める」が四本あって、答えが揃っていない　【読んで確認】

| | 埋めるもの | 壊れているものを見分けるか | アカウントの印を押すか |

**⑬が印を押さないのは、そのままバグです。**印の無い言語は、

### D. その二本が、同じ起動で、待たずに同時に走る　【読んで確認・押していない】

⑬はセッションが立った瞬間に飛び、**答えを待ちません。**
その直後に⑫が飛び、**同じ問い合わせを、同じアカウントに、もう一度出します。**

**弾く材料は、先に走ったほうが書き終えた索引です。**
⑬の答えが返る前に⑫が索引を読めば、**同じ言語が二回入ります。**
しかも二本は**別々の id で入れる**ので（⑫は新しい id、⑬はサーバーの id）、
**同じ言語が、名前も中身も同じまま、二つ並ぶことになります。**

**押していません。**通信の順序が実際にどうなるかは実機で見ていません。

# 二章 ── 一本にした形

**上書きをやめます。**サーバーの一行を書き換えるのではなく、
**番号のついた版を積みます。消さない、書き換えない、足すだけ。**

そうすると「どっちが勝つか」は**番号で決まり**、「戻す」は**「◯番に戻す」だけ**になり、
壊れたものが無事なものを上書きする事故が**構造的に起きなくなります**
── 上書きする場所そのものが無いからです。

**先に一つ、一章で数えていて二章に効く事実があります。**

**いまサーバーに何かが書かれるのは、起動したときと、オンボーディングの扉を
出たときの二回だけです。**（`www/net.js` の同期を呼んでいる所を全部数えて
確認。二か所しかありません。）単語を一つ足しても、その場ではサーバーへ行きません。
**iPhone の中に書かれて、次の起動まで待ちます。**これは量の見積もりを大きく
変えるので、以下ずっとこの前提で書きます。

## 2-1. 何が一つの「版」になるのか

**三通りあります。**数字を並べます。

### 測った数字

**この repo が既に測っているもの**（`docs/DATA_SAFETY.md`。作る前に測った、と
書かれています）:

| | 大きさ |
|---|---|
| 描いた文字 38 個 | 12.1 KB |
| 単語 100 語 | 13.2 KB |
| 単語 5000 語 | **685 KB** |
| 無料の言語まるごと | 約 25 KB |

**このセッションが自分で測ったもの。**アプリと同じ形の言語を作って、
JSON の長さを数えました（走らせて確認）:

| | 大きさ |
|---|---|
| 単語の欄だけ・5000 語 | **587 KB**（一語あたり 120 バイト） |
| 単語の欄だけ・100 語 | 10.3 KB |

**二つの測り方が 15% 以内で合っています。**以下は repo 自身の数字（685 KB）を
使います。

**ここから出る一番大事な事実:**

> **大きい言語では、単語の欄がその言語のほぼ全部（九割以上）です。**

### 三通りの粒度

| 粒度 | 単語を一つ足した起動 一回 | 文字を一つ描いた起動 一回 | 戻すとき人が言うこと |
|---|---|---|---|
| **A. 言語まるごと** | **685 KB** | 685 KB | 「この言語を、あの時点に」 |
| **B. 欄ひとつ**（いまの書き込みの単位） | **685 KB** | 12 KB | 「この言語の単語を、あの時点に」 |
| **C. 一語ごと** | **0.14 KB** | 0.33 KB | 「この単語を、あの時点に」 |

**A と B の差は、思ったより小さいです。**単語が変わった起動では**同じ 685 KB**
です。差が出るのは文字だけを触った起動で、そこは 685 KB と 12 KB で
**五十七倍**違います。

**利点と代償**

**A. 言語まるごと**
- 利点: **一番単純です。**「あの日の言語」が一つのかたまりで、戻すとき
  欄どうしが食い違いません。文字を消して単語だけ戻す、という
  半端な状態が作れません。
- 代償: **文字だけを直した起動でも 685 KB。**一番小さい変更が一番大きい代償を
  払います。
- アプリの作り: いま送っているのは欄ごとなので、**送る側の作り直しが要ります。**

**B. 欄ひとつ**（推す形）
- 利点: **いまの書き込みの単位そのままです。**アプリ側の送り方を変えずに済みます。
  文字だけの起動は 12 KB で済みます。
- 代償: **単語が変わった起動は A と同じ 685 KB。**そして
  **欄どうしの食い違いが作れます** ── 単語だけを三日前に戻すと、
  そのとき無かった文字を指している単語が残りえます。
  （**確かめていません。**単語が文字を指しているかどうか、その形は
  読んでいません。ここは実装の前に読む必要があります。）
- アプリの作り: **送る形は変えなくてよい。**受ける側だけが変わります。

**C. 一語ごと**
- 利点: **量が四千分の一以下**（685 KB → 0.14 KB）。
  「この単語だけ戻す」が言えます。
- 代償: **アプリのほぼ全部を書き換えます。**いま保存する所は**八つ**あって
  （単語と行と名前と書記体系をまとめて書く所、文字、メモ、段階、音、
  キーボード、世界設定、文法）、**そのどれも一覧をまるごと書いています。**
  合わせる所も、断る所も、ファイルに書き出す所も、全部
  「欄は一本の文字列」を前提にしています。
  **これは一本化ではなく、作り直しです。**
- そして**「一本にする」に反します** ── ファイル（三世代）は言語まるごとの
  単位のままなので、サーバーだけ一語ごとにすると**単位が二つになります。**

**このセッションが推すのは B です。**理由は三つ:
1. **いまの書き込みの単位と同じ**なので、アプリ側が変わりません。
   「直すじゃなくて書き換え」を、**受ける側だけに絞れます。**
2. 単語が変わった起動の代償は A と同じで、**A の利点は「食い違いが作れない」
   一つだけ**。それは B に**「戻すのは十二の欄をまとめて」という決まりを
   置けば**同じことです（下の 2-3）。
3. C は量が魅力的ですが、**アプリ全部の書き換えになり、しかもファイルと
   単位が割れます。**

**ただし B を選ぶなら、2-3 の「まとめて戻す」を決まりにしないと、
食い違いが作れます。**そこはオーナーの決めることとして四章に出します。

## 2-2. 番号は何で決まるのか

### 満たさないといけないこと

オーナーが 2026-09-04 に決めた二つです。

```
そもそもバグで消えるなら一生残るはずだよね？自分で消してるわけじゃないし
基本一生残るよな
```
```
普通後から変えたほうになる？アプリ気になるそこ
```

一つ目は**期限も掃除も作らない**ということ。二つ目は
**「どっちが勝つか」を「後から直したほう」で決める**ということです。

### いま番号が三つあって、三つとも誰も比べていません

**一章の G です。**もう一度、二章のために書きます（全部読んで確認）:

| | 誰が付けるか | 誰が読むか |
|---|---|---|
| ファイルの通し番号 | iPhone。上がるだけ | **同期は読まない。**ファイルと設定画面だけ |
| サーバーの行の番号 | **iPhone が「サーバーの番号 + 1」を作って送る。サーバーは上げない** | **誰も比べない。**送り返すだけ |
| サーバーの行の時刻 | **iPhone の時計。送った瞬間** | **取り出す所が一つも無い** |

**そして、いちばん大事なこと:**

> **アプリは「直した時刻」をどこにも持っていません。**

単語にも、文字にも、欄にも、**人がそれを直した時刻は付いていません。**
サーバーの行の時刻は**送った時刻**であって、直した時刻ではありません。
起動しなければ何日も遅れます。

**これがオーナーの決定「後から変えたほうが残る」を満たせない理由そのものです。**
比べるものが無いので、いまは繋がった順で決まっています。

### 用意の仕方 ── 四通り

**ここには CLAUDE.md との衝突があります。先に出します。**

`docs/DATA_SAFETY.md` と保存の通し番号のコメントが、はっきりこう書いています ──
**「時計を使うな。時計が狂った iPhone は毎回勝ってしまい、誰も気づかないまま
その人の作業が巻き戻り続ける」。**だから通し番号は「時計ではない」と
名指しで書かれています。

**そして「後から変えたほうが残る」は、時計を要求します。**

**CLAUDE.md の決まりでは、オーナーが今日言ったほうが勝ちます** ──
「新しい側がオーナーが今しがた言ったことなら、それが仕様であって、
escalate する衝突ではない」。**なので時計を用意する方向で書きます。**
**ただし「時計が狂ったら毎回勝つ」は本当に起きることなので、
それを塞ぐ形を並べます。**

**① そのまま iPhone の時計**
- 直した瞬間の iPhone の時計を、直したものに付ける。
- **一番素直で、一番危ない。**時計が一年進んでいる iPhone は、
  その人の全部の直しが永久に勝ちます。**誰も気づきません。**

**② iPhone の時計 ＋ 二つの箍（推す形）**
- 直した瞬間の時計を付ける。ただし:
  - **後戻りさせない** ── この iPhone がこれまでに見た一番大きい時刻より
    小さい時刻は出さない（一つ足して出す）。
  - **未来を断る** ── サーバーが、自分の時計より大きく先の時刻を**受け取らない。**
    どれだけ先までを許すかは数字なので、**オーナーが決めます**（四章）。
- **狂った時計が勝ち続けるのを、サーバー側で止められます。**
- 代償: **サーバー側に断る所が一つ増えます。**そして
  **断られた書き込みをアプリがどうするか**を決める必要があります
  （黙って直して送り直すのか、人に言うのか）。これも四章。

**③ 見た番号 ＋ 1（時計を使わない）**
- 直すたびに「この iPhone がこれまでに見た一番大きい番号 ＋ 1」を付ける。
- **時計が要りません。**二台が一度でも繋がっていれば、
  後から直したほうが必ず大きい番号を持ちます。
- 代償: **二台が一度も繋がっていない間の直しは、比べられません。**
  そこは結局、繋がった順になります。**オーナーの決定を半分しか満たしません。**

**④ ②と③の両方**
- 番号を主にして、同じ番号のときだけ時計で決める。
- **一番強いですが、持つものが二つに増えます。**
  「一本にする」という今回の話に、二本目を足すことになります。

**このセッションが推すのは ② です。**③ は「後から変えたほうが残る」を
半分しか満たさず、オーナーはその半分（二台が繋がっていない場合）こそを
気にしていました。④ は今回の主旨に反します。

### どこに時刻を付けるか ── 粒度

**オーナーの決定にも「どの粒度で持つか（欄ごとか、スライスごとか）は
決まっていない」と書かれています。**選択肢を並べます。

| | どこに付くか | 効くもの | 代償 |
|---|---|---|---|
| **欄ごと** | 十二の欄それぞれに一つ | 言語の名前、書記体系の向きなど**一つしか入らないもの** | 一番安い。**単語一語の勝ち負けには効かない** |
| **項目ごと** | 単語一語、文字一つに一つずつ | 全部 | 単語一語あたり**十数バイト**増える。5000 語で **60 KB ほど** |

**一章の E で数えたとおり、いま食い違うのは「一つしか入らない欄」だけです。**
一覧の中身（単語・文字・メモ）は**両方足すので消えません。**
**なので欄ごとで、オーナーが気にしていた場面には届きます。**

**ただし届かない場面が一つ残ります** ──
**同じ単語を二台で違う意味に直したとき。**いまは二つの単語として両方残ります
（見出し語が同じなら片方だけ残る、かもしれません。**ここは確かめていません。**
合わせる所は見出し語で同じものと見なすので、**片方が落ちる可能性があります**）。
**ここは実装の前に押して確かめる必要があります。**

## 2-3. 戻すとはどういう操作になるのか

### 人にとって

**いまアプリには、戻す画面が一つもありません。**（`www/` を全部読んで確認。
ファイルから戻すのは起動時に自動で走るだけで、人が押す所はありません。）

**そして「戻す」はオーナーの線では「バグで消えたとき」の話です** ──
「復旧は自分で消した時じゃなくてバグで消えた時の話な」。

**なので選択肢は二つで、これはオーナーが決めます（四章）:**

- **画面を作らない。**戻すのは運営だけ。人は「消えた」と言ってくる。
  **CLAUDE.md の「説明を書くな」にも、画面が増えないことにも合います。**
- **画面を作る。**設定に「前の版」の一覧を出して、選んで戻す。
  **一覧に日付が並ぶので、「いつ直したか」を人に見せることになります。**

### 運営にとって

**戻すのは、その言語のその欄の、選んだ版を「いま」として立て直すことです。**
上書きではありません。**選んだ版と同じ中身を、新しい版として一番上に積みます。**

- **消えるものがありません。**戻したあとも、戻す前の版はそのまま残ります。
  **戻し間違いも戻せます。**
- **オーナーは Supabase のダッシュボードから触れます。**
  押し間違いを減らすなら、管理者だけが呼べる呼び出しを一つ用意して、
  「この言語のこの欄を◯番に」と一行で言えるようにします。

**ただし、これだけでは足りません。一章の A がそのまま残ります。**

iPhone の側が壊れていると、**サーバーを直しても次の起動でまた壊れた版が
上がります。**なので**一本化には、壊れているものを見分ける所（⑩）を
同期の道にも置くことが必ず含まれます。**これは三章で書きます。

## 2-4. どれだけ増えるか

**行が増える条件:** 起動して、中身が本当に変わっていて、送られたとき。
（中身がサーバーと同じなら送られません。読んで確認。）

**一人・一言語・一年。**「単語を直した起動」が一日に何回あるかで変わります。

| 単語 5000 語の言語 | 一日 | 一年 |
|---|---|---|
| 一日 1 回 | 685 KB | **250 MB** |
| 一日 3 回 | 2.0 MB | **750 MB** |

| 無料の言語（25 KB） | 一日 | 一年 |
|---|---|---|

**十人が 5000 語の言語を一日三回直すと、一年で 7.5 GB です。**
**百人なら 75 GB。**

**使っている人の数を知らないので、そこから先は書きません。**

**これは「言語まるごと」でも「欄ひとつ」でもほぼ同じ数字です**
（単語の欄が九割以上なので）。**「一語ごと」にすると四千分の一になります。**

**期限も掃除も作らない、というのがオーナーの決定です。**

オーナーは「その数字は承知のうえ」と決めています。

**ただし、決めていないことが一つ残っています** ──
**この量が置き場の契約の上限を超えたとき、何が起きるのか。**

## 2-5. `supabase/schema.sql` はどう変わることになるか

**書いていません。**どうなるかを文章で書きます。

### 変わるもの ── 五つ

**① 言語の中身の表が、上書きの表から積む表になる**

いまは「言語」と「欄の名前」の二つで一行が決まっていて、
同じ二つで書くと**前の中身が消えます。**
これを**「言語」と「欄の名前」と「版の番号」の三つで一行が決まる**形にします。
同じ言語の同じ欄が、版の数だけ並びます。

**② 書き換える道と消す道を、この表から外す**

いま、この表には**書き換える道も消す道も用意されています**（読んで確認）。
**積む表になったら、その二つは無くなります。**
公開の記録の表が既にその形です ── **書き換える道も消す道も無いから記録なのだ**、と
`supabase/schema.sql` 自身が書いています。**同じ形にします。**

**言語ごと消したときだけは別です。**言語の行が消えると、
その言語の中身は今も自動で一緒に消えます。**版も同じように消えます。**
これはオーナーの線（自分で消したものは戻さない）のとおりです。

**③ 「今のこれ」を答える所を、一つ作る**

いまサーバーの中で、この表を**「一行しかない」前提で読んでいる所が三つ**あります
（読んで数えました）:

- 言語のページを開けるかどうかを決める所（世界設定の欄を読む）
- 言語の単語の数・文字の数を数える所
- 誰がこの言語の中身を読んでよいかを決める所

**この三つは全部、「一番新しい版」を読むように直す必要があります。**
一つ一つ直すのではなく、**「一番新しい版」を答える所を一つ作って、
三つともそこを読む**形にします。**一箇所です。**

**④ アプリが読む形も、そこ一つになる**

iPhone が言語の中身を取りに行くとき、いまは全部の行を取ってきます。
**版が積まれると、全部の版が返ってきてしまいます。**
③で作った「一番新しい版」を読むようにします。**アプリ側は一行の変更です。**

**⑤ 時刻を受け取る所と、断る所**

2-2 の②を採るなら、**「直した時刻」を受け取る欄**が要ります。
そして**自分の時計より大きく先の時刻を断る**仕掛けが要ります。
**どれだけ先まで許すかはオーナーが決める数字です。**

### 変えないもの

- **公開の記録の表** ── 既に積む表です。触りません。
- **投稿・下書き・写真・声** ── 今回の一本化は**言語の中身だけ**です。
  オーナーの決定の「Area」も保存・同期・バックアップ・復元・運営側の復旧で、
  投稿は入っていません。**投稿と写真と声に版も履歴も無いことは、
  一章の H として穴のまま出してあります。**

### 忘れてはいけない一つ

**`supabase/schema.sql` が変わったら、二人目の検査を回す必要があります**
（`npm run rls`）。**これは `schema.sql` が変わったときにしか赤くならない
検査です。**このセッションは回していません（コードを変えていないので）。

## 二章で押して確かめたこと・確かめていないこと

**走らせたこと**

- **版一つの大きさ。**アプリと同じ形の 5000 語を作って測りました
  ── 単語の欄だけで 587 KB、一語 120 バイト。
  repo 自身の数字（685 KB）と 15% 以内で合っています。
- **サーバーに書かれるのが起動と扉の二回だけであること。**

- **サーバーの中で言語の中身を「一行」前提で読んでいる所が三つあること。**

**読んだだけ・押していないこと**

- 番号と時刻を誰も比べていないこと。
- 戻す画面がアプリに一つも無いこと。
- 単語が文字を指しているかどうか（欄ごとに戻したとき食い違うか）。

  **押して確かめる必要があります。**

**確かめていないこと**

- **一年の量は、使っている人の数を知らないので一人ぶんまでしか書いていません。**
- 置き場の契約の上限。**ダッシュボードは見ていません。**
- 実機では何も押していません。

# 三章 ── 何を消すか

**ここが一番大事です。**

```
A new mechanism covering the old one's gap is the one thing that must not
happen: from then on the feature runs on two and nobody can say which is
deciding. And the old one is deleted -- not kept beside the new one, not
「as history」, not 「just in case」.
```
CLAUDE.md「Simple, and a bug is REWRITTEN, not patched」

**新しいものを足して古いものを残したら、十四本が十五本になります。**
一本ごとに、消すのか残すのかを名指しで書きます。残すものには、
**なぜそれが二本目にならないのかを一行で**添えます。

## 消すもの ── 五つ

### ① 言語の中身を、上書きすること　【消す】

**これが今回の中心です。**サーバーの一行を書き換える道が無くなります。
**書き換える所と消す道を、この表から外します。**
公開の記録の表が既にその形で、`supabase/schema.sql` 自身が
**「書き換える道も消す道も無いから記録なのだ」**と書いています。

**消えるバグ:** 一章の A（壊れた一本が無事なサーバーを上書きする）と、
一章の E の五行目（サーバーへ書くとき iPhone が必ず勝つ）。
**上書きする場所が無くなるので、構造的に起きなくなります。**

### ④ 「最後に合意した中身」の控え　【消す。仕事は版の番号が引き継ぐ】

いま iPhone は、**十二の欄それぞれについて、中身をもう一部持っています。**
「この iPhone とサーバーが最後に合意した中身」の丸ごとの写しです
（`netAgreed()` を読んで確認 ── 中身をそのまま書き込んでいます）。

**つまり iPhone は今、全部の欄を二部ずつ持っています。**
5000 語の言語なら、685 KB ではなく **1.4 MB** です。

**版が積まれれば、これは番号一つで足ります。**
「最後に合わせたのは◯番」と控えておけば、その中身は**サーバーに在ります。**

- **消えるもの:** iPhone の中の重複した写しが十二本。5000 語の言語で **685 KB。**
- **これは一章の B（保存の失敗が黙って済まされる）にも効きます。**
  ストレージが満杯になりにくくなります。
- **控えの役割そのものは消えません。**「消したのか、聞いていないだけか」を
  分ける仕事は残り、**番号一つがそれを答えます。**

**これは足すのではなく、置き換えです。**丸ごとの写しは消えます。

### ⑨ 縮む書き込みを断る所　【消す ── ただしオーナーの一行が要ります】

**この所のコメント自身が、こう書いています** ──
「合わせる所が既に両方足して、読めないときは iPhone の側に落ちるので、
**これは決して火を吹かないはずだ。だからこそ置いてある。一回の比較で済むし、
火を吹く日は上流の何かが変わった日だ**」。

**版が積まれると、断る理由が無くなります。**小さくなった結果が来ても、
**前の版はサーバーに残っています。**取り返せます。
**「小さいから書かない」は、そのとき「新しい版を記録しない」という意味になり、
それはこの app が一番避けている形 ──「守るものが勝ってしまう」── の裏返しです。**

**消すべきだと読みました。ただし、これは守りを一つ外す変更です。**
**「どっちが勝つか」はオーナーのものなので、四章に一行として出します。**

### ⑬ サーバーから言語を降ろす所・その二　【消す】

**一章の C と D です。**同じ仕事をする関数が二本あり、
**同じ起動で、待たずに、同じ問い合わせを二度出しています。**

| | ⑫ 残すほう | ⑬ 消すほう |
|---|---|---|
| 言語の id | 新しく作る（サーバーの id は別の欄に控える） | サーバーの id をそのまま使う |
| アカウントの印 | **押す** | **押さない** |
| 所有を見る所のコメントに名前が | **在る**（言語を作る五つの道の一つとして） | **無い** |

**⑫を残します。**理由は二つ:
- **印を押します。**⑬が押さないのはそのままバグで、印の無い言語は
  一覧に出ません（一章の C）。
- **id の作り方が、app の他の全部と揃っています。**この iPhone で作った言語も
  「自分の id ＋ サーバーの id」の形なので、⑫はその形のままです。

**⑬が持っていた利点は失われません。**⑬のコメントは「サーバーの id を
そのまま使うと『もう持っているか』の判定が正確になる」と書いていますが、
**⑫も判定にはサーバーの id を使っています**（読んで確認）。

**消えるバグ:** 一章の C（印を押さない）と D（同じ言語が二つ入りうる）。

### ⑮ `docs/RECOVERY.md` の案A の節　【消す ── この文書に置き換わる】

**案A は、この文書そのものです。**両方残せば、**同じ設計が二つの文書に
書かれることになります。**CLAUDE.md の「古い規則残りすぎ」がそれです。

- **案A の節は消して、この文書を指す一行にします。**
- **案B（消える直前の行を写す）は今回は作りません。**投稿・下書き・写真・声の
  話で、オーナーの決定の Area に入っていません。**残す穴として、一章の H に
  書いてあります。**案B の節は残しますが、**「今回はやらない」と書き足します。**
- **案C（データベース全体を巻き戻す）は⑯そのものです。**下に書きます。

## 残すもの ── 十本

### ② 公開の記録　【残す】

**答えている問いが違います** ──「これを先に作ったのは誰か」。
中身ではなく指紋しか入っておらず、**保存にも復元にも一度も読まれません。**

### ③ iPhone の写し　【残す】

**答えている問いが違います** ──「電波が無いときに何が読めるか」。
**版ではありません。**版を積んだあとは「まだ送っていない分」になります。
**これは決めるものではなくなります** ── 決めるのは番号です。

### ⑤ 保存の通し番号　【残す】

**形が違います。**通し番号は**言語一本につき一つ**で、
版の番号は**欄ごと**です。一緒にすると、
**「十二の欄の中で一番大きい番号」という三つ目の形を作ることになります。**
それは一本化ではなく発明です。

**そして答えている問いが違います** ──「このファイルは何世代目か」。
**同期はこれを読みません**（読んで確認）。

### ⑥ 別アカウントのものを預ける所　【残す】

**答えている問いが違います** ──「この iPhone に今いるのは誰か」。
保存の道にも復元の道にも立っていません。

### ⑦ ファイルの三世代　【残す ── リーダーの読みに同意します】

**リーダーの見立てはこうでした:**

> ファイルは「サーバーにも iPhone の中にも何も無いときの最後の一枚」で、
> 役割が違うから二本目ではない

**同意します。確かめたのはこの三つです:**

1. **その iPhone と一緒に無くなります。**運営から見る道が**一つもありません**
   ── 運営の画面に在るのは数字四つと、投稿を隠すこと、アカウントを止めることだけ
   （`www/mod.js` を読んで確認）。
2. **全部の版を置くには小さすぎます。**二章の数字で、5000 語の言語を
   一日三回直す人は**一年で 750 MB**です。三世代なら **2 MB** です。
   **三百倍以上違います。**
3. **役割が本当に違います。**版はサーバーに在り、サーバーが無いときには
   一枚も読めません。ファイルは**サーバーが無いときにだけ意味があります。**

**ただし、一つだけ変わります。**壊れているかを見分ける所（⑩）が、
**いまファイルの道にしかありません。**一本化のあとは、**同じ一箇所を
両方の道が読みます。**ファイル側に二本目を作るのではありません。

### ⑧ 合わせる所　【残す ── ただし中身を書き換える】

**ここは注意が要ります。**

> **版を積むことは、合わせることの代わりにはなりません。**

**なぜか。**版だけにすると、二台で別々に単語を足したとき、
**後から積まれた版が、相手の足した単語を持っていません。**
一番新しい版が今なので、**相手の単語が消えます。**
**いまより悪くなります。**

**答えている問いが違うからです:**

- **合わせる所** ──「二人が別々に足したものを、どうするか」
- **版** ──「いつの状態に戻れるか」

**なので残します。ただし三つ書き換えます:**

1. **一つしか入らない欄の答えを、「後から直したほう」に。**
   （オーナー 2026-09-04。いまは「iPhone が勝つ」）
2. **「読めない＝無い」をやめる。**壊れているものは、
   **無いものとして扱わず、相手側を返します。**これが一章の A の直しです。
   **足すのではなく、その一行を書き換えます。**
3. **控えを、丸ごとの写しから番号に。**（④）

**この所の冒頭のコメントも書き換えます** ──
「どちらの側も新しさで勝たない」は、**もう本当ではなくなります。**

### ⑩ 壊れているかを見分ける所　【残す ── 一箇所のまま、読む道を増やす】

**いま一箇所に在ります**（十二の欄それぞれについて、これは配列・これは文字列、と
形が決まっている所）。**問題は在ることではなく、読む道が片方しか無いことです。**

**同期の道にも同じ所を読ませます。二本目は作りません。**
CLAUDE.md の「一つの規則は一つの場所にあって、従う所はそれを言い直さない」が
そのままこれです。

### ⑪ ファイルから戻す所　【残す】

**答えている問いが違います** ──「サーバーにも iPhone にも無いとき、
何を埋めるか」。**有るものには触らない、という決まりは変えません。**

### ⑭ 下書きを降ろす所　【残す ── 今回は触りません】

**下書きは言語ではありません。**オーナーの決定の Area
（保存・同期・バックアップ・復元・運営側の復旧）は言語の中身の話で、
投稿と下書きは入っていません。

**ただし、下書きにも投稿にも版はありません。**穴として一章の H に
書いてあります。**今回広げません。**

### ⑯ サーバー自体のバックアップ　【残す ── というより、作る】

```
サーバーのバックアップも必要で。
```
オーナー 2026-09-04

**答えている問いが違います** ──「土台そのものが壊れたら」。
版はデータベースの中に在るので、**データベースごと失われたら版も無くなります。**

- **`supabase/setup.md` に一言も書かれていません**（検索して 0 件、確認済み）。
- **入っているかどうかも、契約している段も、確認していません。**
  **ダッシュボードは見ていません。**
- **これは `docs/RECOVERY.md` の案C そのものです。**
  案C の節は残し、**「これは⑯であって、案ではなく決定」と書き換えます。**

### ⑰ 消す口の台帳と DELETE REVIEW　【残す】

**走る仕組みではありません。**新しい穴が開くのを止める門です。
**消えたものを戻す役には立ちませんが、二本目でもありません。**

# 四章 ── 移り方と、オーナーへの質問

## 4-1. いまある言語をどう移すのか

**移行は写すものです。読んだものを消しません。**

```
A migration copies and never removes what it read.
```
CLAUDE.md「Data」

### サーバーの側

**いまサーバーに在る一行が、そのまま「一番目の版」になります。**

**写します。消しません。**
新しい形の置き場を作り、**いま在る行を一行ずつ、一番目の版として写します。**
写し終わって、読めることを確かめてから、**別の作業として**古い置き場を片付けます。
**片付けるときには DELETE REVIEW を書きます**（`docs/DATA_SAFETY.md`）。

**アプリを一行も変えずに済ませられます。**
いまアプリは「この言語の欄を全部ください」と訊いています。
**その訊き方に、「一番新しい版だけ」を答えるようにできます。**
アプリから見ると、**返ってくるものは今日とまったく同じです。**
書くほうも同じで、**アプリが今の形で書き込むと、それが新しい版として積まれます。**

**これは二本ではありません。**置き場は一つで、
**訊く口と積む所が、同じものの表と裏です。**

### iPhone の側

**移すものが一つあります** ── 三章の④、丸ごとの控え十二本です。
**番号一つに置き換わります。**

- **新しく控えるもの:**「最後に合わせたのは◯番」。
- **消えるもの:** 丸ごとの写し十二本。5000 語の言語で **685 KB。**
- **これは削除なので、DELETE REVIEW が要ります。**
  書く内容ははっきりしています ──
  **人が作ったものではありません。**この iPhone とサーバーが**両方すでに
  持っている**ものの写しで、`tools/store-check.mjs` の中のこの鍵の説明自身が
  「人の作ったものではない」と書いています。**失っても、一回ぶん忘れるだけです。**

**順番:** 番号を控え始めてから、写しを消します。**逆にすると、
その一回だけ「消したもの」が戻ってきます。**

### 移らないもの

- **一度もサーバーに上がっていない言語。**サーバーに無いので版もありません。
  **ファイルの三世代が、そのままそれの守りです。**（三章⑦）
- **投稿・下書き・写真・声。**今回の Area に入っていません。（三章⑭）
- **サーバーに写しの無いもの** ── 設定の 20 欄、書記体系、テーマ、表示言語。
  **これは「サーバーに道を作る」という別の仕事です。**復旧の話ではありません。

## 4-2. どういう順でやるか

**どこで区切れば、途中で止まっても壊れないか**で切りました。
**一から三は、止まってもアプリの振る舞いが一つも変わりません。**

### 一. サーバー自体のバックアップを確かめる／入れる　【コードは一行も変わりません】

**土台です。**版はデータベースの中に積まれるので、
**データベースごと失われたら版も無くなります。**

**やること:** ダッシュボードを見る。契約している段を確かめる。
巻き戻せる幅を確かめる。**`supabase/setup.md` に書く。**

**止まったら:** 今日と同じです。何も変わりません。

### 二. サーバーの側だけ、積む形にする　【アプリは一行も変わりません】

置き場を新しい形にし、いま在る行を一番目の版として写す。
訊く口が「一番新しい版」を答えるようにする。
**サーバーの中で「一行しかない」前提で読んでいる三つの所も、
その口を読むように直す**（二章 2-5 の③）。

**止まったら:** **アプリから見て、今日とまったく同じです。**
返るものも、書けるものも変わりません。**版が積まれ始めるだけです。**

**ここで `npm run rls` が必ず要ります。**置き場の形が変わるので、
**この検査はここでしか赤くなりません。**

### 三. アプリが「直した時刻」を持ち始める　【誰もまだ読みません】

保存する所が、直した瞬間の時刻を書く。**まだ誰も比べません。**

**止まったら:** 何も変わりません。**書かれるだけで、読まれません。**

### 四. 合わせる所を書き換える　【ここが振る舞いの変わる一歩です】

### ① 版は、どの大きさで積むか　【これが無いと始まりません】
