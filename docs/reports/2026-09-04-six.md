## 1. 検索の画面が、検索していないのにずっと回る ── ①

**確かめた。**押して見ました。

**何が起きているか。**「探す」のタブを開いて何も打っていないとき、画面の
まん中でダイヤの印が回り続けます。止まりません。**サーバーが正常でも止まりません。**

三つの状態で試して、三つとも回り続けました（0.5 秒後・3 秒後・8 秒後を読んだ）:

| サーバー | 8 秒後 | 履歴が来たか |
|---|---|---|
| 正常。履歴は空で返す（新しいアカウント） | **回っている** | 来た |
| `recent_search` が無い（404） | **回っている** | 来ない |
| 何も答えない | **回っている** | 来ない |

絵は `shots/six-explore-ok-empty.png`（このディレクトリは commit されません）。

**どこか。**

| | |
|---|---|
| `www/sns.js:1588` | `snsRecentHTML()` ── `if(!a.length) return (netSignedIn() && !snsRecentGot)? snsWaitHTML() : '';` |
| `www/sns.js:1501-1512` | `snsRecentPull()` ── 印を立てる所 |
| `www/sns.js:1682` | `snsHitsHTML()` ── 打っていないときは履歴を描く |

**なぜそうなっているか。特定しました。同じ関数に二つ、別々の欠陥があります。**

**一つ目 ── 答えが来ても描き直さない。**`snsRecentPull()` は
`snsRecentGot=true` を立てたあと、`if(snsSameWords(got, snsRecent())) return;`
で帰ります。**履歴が空で、この iPhone の写しも空なら、二つは同じなので
そこで帰り、`render()` に届きません。**印は立っているのに画面が古いままで、
回っている絵がそのまま残ります。**サーバーが正しく答えたときに起きます。**

**二つ目 ── 落ちたときは印が立たない。**失敗の側は
`function(){ snsRecentAsk=false; }` だけで、`snsRecentGot` は偽のままです。
描き直す所も、もう一度訊く所も、諦める所もありません。**`recent_search` は
2026-09-03 に足された新しい表で、`docs/STATE.md` はスキーマをまだダッシュ
ボードに流していないとオーナーの宿題に書いています。**流れていなければ、この
表への問いは毎回落ちます。

**同じ形が他に三つあります。押して確かめました。**サーバーが答えないとき:

| 画面 | どこ | 8 秒後 |
|---|---|---|
| タイムライン | `www/sns.js:755`（`SNS_GOT`） | 回っている |
| 通知 | `www/sns.js:2027`（`NOTES_HAVE`） | 回っている |
| 人の言語のページ | `www/home.js:1680`（`WLDS_HAVE`） | 回っている |

**推測（読んだだけ）。**同じ欠陥がもう二箇所あります ──
`www/me.js:1066-1077` の `folPull()`（人のフォロー一覧。失敗すると
`FOL_ASKED[k]=0` に戻すだけで描き直さない）と、`www/sns.js:285` の
保存した検索。

**直し方の案。**`snsRecentPull()` を、`www/store.js:353` の `storeCurAsk()` と
同じ形にする。**この形はこのリポジトリに既に在って、正しく動いています** ──
成功でも失敗でも `STORE_GOT=true` を立て、どちらでも描き直す。つまり:

1. 失敗の側でも `snsRecentGot=true` を立て、`render()` を呼ぶ。
2. 成功の側は、写しと同じでも `render()` を呼ぶ（`save()` は要らない）。

**二つ目の案（推さない）。**九箇所ぜんぶを一つの仕掛けに寄せる。正しいけれど
大きく、今日の一件を止めるには要りません。**4 番に書いてあります。**

**オーナーに聞くこと。**検索の履歴が本当に空だったとき、画面には何を出しますか。
いまの作りは「何も出さない」です（回るのをやめれば白い画面になります）。

## 4. 数字が、サーバーに聞く前に出て、あとから変わる ── ②

**確かめた。**押して見ました。**フォロー数だけではありません。五箇所あります。**

サーバーの返事を 1.5 秒遅らせて、0.3 秒後と 2.8 秒後を読みました:

| 画面 | 0.3 秒後 | 2.8 秒後 | |
|---|---|---|---|
| 自分のプロフィール | `0 Following` `0 Followers` | `3` `2` | **押して確かめた** |
| 人のプロフィール | `0 Following` `0 Followers` | `12` `34` | **押して確かめた** |

**どこか。**

| | 何 | |
|---|---|---|
| `www/me.js:493` `:495` | 自分の フォロー中／フォロワー。`meFollowing().length` をそのまま出す | 確かめた |
| `www/me.js:890` `:892` | 人の フォロー中／フォロワー。`String(p.fo||0)` ── **答えが無い時に 0 と書く所** | 確かめた |
| `www/settings.js:929` `www/store.js:434` | **プラン画面の値段。**`storeCost()` が空を返す間、`t(p.mo)` の打ち込みの `$4.99` が出て、App Store が答えると入れ替わる | 推測 |
| `www/post.js:2587` `:3074-3076` | 投稿の 返信／リポスト／いいね の数。`postAct()` は 0 のとき何も出さないので「無い→7」の形 | 推測 |
| `www/shell.js:1109` | タブの通知バッジ。`notUnread()` が 0 より大きい時だけ出るので、これも「無い→1」 | 推測 |

**なぜそうなっているか。特定しました。**データの側は正しく作ってあります ──
`www/me.js:589` の注が書いている通り、`whoOf()` は答えの無い数字を
`undefined` のまま持ち、0 とは区別しています。**壊しているのは描く所です。**
`String(p.fo||0)` の `||0` が、「まだ誰も数えていない」を「0 人」に変えて
画面に出しています。自分の側は `undefined` すら持たず、`ME.fo` という写しの
長さをそのまま出しています。

**値段だけは仕掛けが別です。**`storeHeld()`（`www/store.js:308`）が待つのは
`current`（持っている段）の答えで、**値段（`products`）は待ちません。**
二つは別の印（`STORE_GOT` と `STORE_P`）なので、待ちの門を通ったあとに
打ち込みの値段が出ます。

**直し方の案。**数字の場所に、答えが来るまで印を出す。オーナーの言葉
「サーバーに聞く前にロード挟んで絶対に遅れて表示させることないように」
のとおりです。

一箇所を作って、五箇所がそれを使う形を推します（**二つ目の案は、五箇所を
それぞれ直すこと。数が同じなら一箇所のほうが良い、というだけの理由です**）:

1. 「答えが来たか」を各所が持つ（人の側は `p.fo!==undefined` で既に答えられる。
   自分の側は `FO_ASKED` の隣に「来た」の印が要ります）。
2. 来ていない間は数字ではなく待ちの印を出す。**`||0` をやめる。**
3. 値段は、`products` が答えるまで値段の場所を待ちにする。落ちたときは
   `storeSay()` が既に持っている状態の文を出す（`store.fail` / `store.nosale`）。

**オーナーに聞くこと。三つあります。**

1. **自分のプロフィールの数字。**この iPhone には前回の答えの写しがあります。
   「写しをすぐ出す（速いが、あとで変わることがある）」と「答えが来るまで
   出さない（絶対に変わらないが、一瞬空く）」のどちらですか。
   **2026-09-02 に「snsで一瞬何も出ないとかあり得んやろ」と言われているので、
   ここは私では決められません。**
2. **投稿のいいね・リポスト・返信の三つ。**同じ扱いにすると、投稿一つに
   小さい印が三つ並んで回ります。それでよいですか。
3. **通知のバッジ。**丸の中に印は入りません。数字が出るまで丸ごと出さない、で
   よいですか（いまもそうなっています）。

## 7. 待ちの印が九箇所に散らばっていて、どれも「落ちた時」を持っていない ── ④

**リファクタリングの四つの理由のうち「バグを生んでいる重複」です。**
きれいにしたいからではありません。**1 番はこの重複が生んだものです。**

**確かめた。**`grep -rn "snsWaitHTML()" www/*.js` で **九箇所**。

**何が起きているか。**印を描く関数は `www/sns.js:42` の一つですが、
**「答えが来たか」を憶える仕掛けは九箇所がそれぞれ別に持っています** ──
`SNS_GOT` / `snsSavedGot` / `snsRecentGot` / `NOTES_HAVE` / `LANG_WAIT` /
`WLDS_HAVE` / `FOL_HAVE` / `STORE_GOT` / `got`。**九つのうち、落ちた時と
時間切れの両方を持っているのは `www/store.js` の一つだけです。**

- 落ちた時に印を止める: `store.js` だけ（`storeCurAsk()` の `catch`）
- 時間切れを持つ: `storeAsk()` だけ（`STORE_WAIT` = 25 秒）
- **`www/net.js` の `netSend1()` に `x.timeout` はありません。**答えないままの
  接続を切る所がどこにもない、という意味です（推測 ── 実機で何秒で切れるかは
  WKWebView 側の既定で、押さないと分かりません）

**なぜこれが重複なのか。**同じ問い（「まだ来ていない・来た・来なかった」）に
九つの答えがあり、**そのうち三つで実際にバグになっているのを今日押して
確かめました**（1 番の表）。

**直し方の案。**九箇所を一つの仕掛けに寄せる。`storeCurAsk()` が既に持って
いる三つ ── 成功で立てる・失敗でも立てる・時間切れで立てる ── を持った
小さなものを一つ作り、九箇所がそれを使う。

**ただし、1 番より先にやることではありません。**1 番は二行で止まります。
**振る舞いの変更とリファクタは同じコミットに乗せない**（`CLAUDE.md`）ので、
順番は「1 番を直す → 緑を見る → 寄せる」です。
