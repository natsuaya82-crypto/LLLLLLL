## 直したこと

**① 上限の基準を、一番大きい端末から一番小さい端末へ。**

2026-08-26 に「上限は全機種で一つの数」にしたのは正しいのですが、**基準を
390×844 に取ったのが逆でした。** 幅の規則は rule 19 が「一番細い iPhone は 320」
と一番小さい方を基準にしています。同じにすると:

```
floor((568 × 0.55 − 52) / (320 × 0.1385)) = 5
```

| | 5行の高さ | 画面比 |
|---|---|---|
| SE 1 (320×568) | 274pt | **48.2%** |
| SE 2/3 | 312pt | 46.7% |
| 15/16 | 322pt | 38.2% |
| 16 Pro Max | 357pt | **37.3%** |

**全機種で半分以下**なので、「入力欄も含めて50パー」に `KB_MOST` を変えずに
収まりました。**5 は無料 QWERTY の行数そのものです。**

**② 編集画面の1行を、端末なりに。** `--kh:44px` の固定ピクセルが原因で、
シートはどの端末でも 388px ── **SE 1 で 68.3%。これが「7割」です。**
`kbSheetH()` が `--kbw × KB_ROWW` を置きます（`kbSheetW()` と同じ手）。
**SE 1 で 68.3% → 44.7%。`index.html` は触っていません。**

**③ 左右寄せは半キーを無視する**（オーナー決定）。`if(lead%2) lead--` を
中央寄せだけに。**前日の決定と噛み合います** ── 半キーずれた行はどの列にも
掛からないので光りません。

## 上限が5になって壊れた二つ（どちらも直しました）

**「無料はそもそも動かさないんだから関係ないだろ？」** ── そのとおりで、
**board 0 本体は編集できません。** 壊れたのは **qwerty パターンから作った盤**
の方です。あれは無料のを写した5行の盤で、**編集できます。** 上限が5になった
瞬間、行も2ページ目も足せなくなりました。

- `kbLayPut()` が「最後の行に空きが無ければ新しい行」しか知らず、5行×合計10 の
  盤では両方だめでした。**`kbFacePut()` に寄せて一箇所に** ── 隙間 →
  スペースが1キー分譲る → 新しい行。スペースが払うのは `kbDefault()` が
  `123` キーで昔からやっていることです。
- **隙間は「1キー以上」に限りました。** QWERTY 3行目の `gap:0.5` が層キーに
  化けて、**幅0.5（390pt で14pt）の押せないキー**になっていました。

## 実機側 ── **触っていません。一行残っています**

`ios/` は今日 `claude/plan2` が持っているので触りません。

**写真は cap（55%）を超えて見えます。** `place()` は `view` の高さを
`min(want, cap)` で止めますが、**iOS はその下にホームインジケータぶんの安全域を
足します** ── 0.55 × 956 = 526pt に約34pt が加わると 58.6%、写真とほぼ一致します。

**第一容疑はこれですが、Linux では確かめられません。** 差分案:

```swift
// place() の中
let inset = view.safeAreaInsets.bottom
let cap = UIScreen.main.bounds.height * KeyboardViewController.mostOfScreen - inset
```

システムに聞くだけなので、0 が返れば何も変わりません。**実機で見てから**。

**`KB_MOST` は 0.55 のままにしました。** 5行なら全機種で 50% 以下に収まるので、
変える必要がありませんでした。もし 0.50 にするなら **`KeyboardViewController` の
`mostOfScreen` と `www/keyboard.js` の `KB_MOST` を同じコミットで** ──
`kb-check` が Swift から読んで突き合わせているので、片方だけだと赤になります。

## 検査

`tools/kb-check.mjs` に9項目。**編集画面の高さは 320×568 のページをもう一枚
立てて測ります** ── 固定 44px と正しい答えは、この検査がふだん走る 390 では
**1px も違いません。それがこの不具合が生き延びた理由そのものです。**

**赤を四通り見ました:**

```
(1) 基準を 390x844 に戻す
    FAILED  so a board at the ceiling is inside the cap on EVERY phone:
            320x568 -> 63.8%, 375x667 -> 62.3%
    FAILED  and inside half the screen too -- worst is 63.8%
(2) 編集画面を 44px 固定に戻す
    FAILED  the sheet in the app is a row of 44px on a 320pt phone,
            which is its own width x 0.1385 (36.8) -- not a flat number
(3) 半キーの隙間も層キーに使う
    FAILED  and the space bar gives up a key for it when every row is full (6 -> 6)
(4) 左右寄せで半キーを丸める
    FAILED  and hard against the right: all 14 half columns in front, half key and all
```

**(2) は、二枚目のページを立てなければ緑のままでした。** 一度そのまま緑を
見ています。

## 動かしていないもの

**既に上限を超えて保存されている盤は一切動きません**（規則19、`overKept` と
`overStillCant`）。7行で作った盤が5行に切られることはなく、足せなくなるだけです。

`tools/fixture.mjs` の面を1つ、行を1つ空けてから選ぶように直しました ──
qwerty パターンの盤が上限ちょうどになったので、`＋` が消灯して `kbIns` に
届かなくなったためです。

## 実機で見るもの

1. **5行より多い盤が新しく作れないこと。**
2. **編集画面のシートが、小さい端末で小さくなること**（SE で 44.7%）。
3. **qwerty パターンの盤に2ページ目が足せること**（スペースバーが1キー分縮む）。
4. **右寄せで半キーが端に残ること。**
5. **上の差分を入れたあと、キーボードが画面の半分に収まること。**
