## 2-1 ＋ 2-3(b) ── フリックのキーが QWERTY のキーと同寸だった

**原因。** `kbSheetW()` が `--kbw / 20 × その面の列数` を返していました。列幅は
固定なので、**十キーより狭い面は短冊になり、その上に乗っている物が全部一緒に
縮みます。** 390px の画面で測った値:

| | 前 | 後 |
|---|---|---|
| qwerty のシート / キー | 323.7px / **28.2×44** | 323.7px / **28.2×44** |
| flick のシート / キー | 97.1px / **28.2×44** | 323.7px / **103.7×44** |
| tap・chart のシート | 161.8px | 323.7px |
| 作ったばかりの2ページ目のシート | 64.7px | 323.7px |
| その面の「行を足す」破線＋ | **60.5px** | **319.5px** |

**最後の行が 2-3(b) です。**「8列も追加できるのに行は2ページ目から追加できない」
── **行はずっと足せていました。** `kbRoomRow()` も `kbAddRowNew()` も
`kbLayer()`（見えている面）を読んでいて面ごとに正しく、`kb-check` で
1→2→3 と増えるのを見ています。足せなかったのではなく、**押す的が 60px でした。**

**実機は最初から正しかった。** `KeyBoardView.layoutSubviews` は
`free * key.width / その行の合計`。読み取り専用の盤（無料プランの顔）も
`flex: key.w`。**エディタだけが三つ目の意見を持っていました。**

**直し方。** `kbSheetW()` は常に `var(--kbw)`。グリッドが
`repeat(--kc, 1fr)` なので、キーの取り分は勝手に「行の中のキー数ぶんの1」に
なります。`kbCellW()` は十キーの尺のまま残し、**1・2・3 の幅の見本専用**に
しました ── 見本は割合の見本で、3キーの盤で実寸にすると3枚で画面の2倍になり、
それが 2026-08-25 が直した `tools/side-baseline.txt` の3行です。直ったまま。
掴んだキーの影は `kbKeyW()`（新規）でシートの実寸に合わせます。

**2026-08-25 の決定を置き換えました**（`docs/FEATURE_RULES.md`、同じコミット）。
「エクセルみたいに…横幅が固定されるはずだよ」。**あの決定が守ろうとしたものは
残り、むしろ強くなっています**: 列を消しても盤の端は動きません（前は widest row
が変わるたびにシート幅が動いていた）。失っていたのは、人が打つキーの大きさの
方でした。

**高さは変えていません。** 横は実機と同じ形になりましたが、縦は行数に関わらず
1行の高さ（44px）が決まったままです。`docs/keyboard.md` がそう書き直して
あります ── 同じ文が「拡大すれば実機と同じ形です（高さも幅も同じ比で縮めて
あります）」と言っていて、**十キーより狭いどの盤についても嘘でした。**

**赤を見た。** `kbSheetW()` を元に戻して `npm run kb` → **4行赤**、うち一行が
オーナーの問いそのものです:

```
FAILED  a flick board and a QWERTY board are drawn the same width
FAILED  and a flick key is not a QWERTY key: 28.2px against 28.2px
FAILED  and taking a column out does not move the board's edges
FAILED  the row-adding + is the same size on page 2 as on page 1 (61px)
```

**言っておくこと**: `each is its share of the row it is in` の一本だけは
バグを戻しても**緑のまま**でした ── 列固定でも「シート幅÷列数」は成立するから
です。その一本では捕まりません。並べた4本が要ります。

## 2-2 ── 面は出口を失う

**原因。** `kbAddLay()` は**作る瞬間**については正しくやっていました（rule 19
のとおり、行く道を今の面に、戻る道を新しい面に）。何も持っていなかったのは
**その後**です。シートの削除は行と列でキーを取り、戻り道はキーです。

作ったばかりの2ページ目（1行・戻り道と空きキー1つ）に立って行番号を押すと:

```
前      [[1],[0]]
行削除   [[1],[]]     ← face 1 は rows 1 → 0
列削除   [[1],[]]
```

**行ゼロの面**は、電話では何も出ていなくてどこにも行けないキーボードです。
どちらも throw しません。編集画面は何も無い面を描き、タブは 2 と言い続け、
26 のチェックは全部緑でした。**実機で打った人にしか届きません。**

**直し方。** 二つ。

- **`kbWayOff()`** ── 面が2つ以上ある盤で、出口のキーを1つも持たない面に1つ
  入れます。**足すだけで、何も消しません。** 置き場所は `kbLayPut()`、
  `kbAddLay()` と同じ（最後の行の先頭、入らなければ新しい行、既存キーの上には
  置かない）。呼ぶのは **`saveKb()` 一箇所** ── `kbNoted()` と同じ理由で、
  キーボードへの変更は必ず `saveKb()` で終わるので忘れようがありません。
  `kbDelRow`・`kbDelCol`・`kbDelKey` の三箇所に同じ三行を書く案は捨てました。
  **直しでもあります**: 前のビルドで戻り道を失った2ページ目は、その
  キーボードを次にいじった瞬間に取り戻します。歩くのは `kbEdit()` の一枚だけ
  で、誰も見ていない盤は触りません。
- **`kbDelRow()` に床** ── 面の最後の1行は消えません。`kbDrop()` の
  「never the last one」を一段下で言ったものです。面を無くすのはタブの横の ×。

**赤を見た。** 両方を外して `npm run kb` → **5行赤**。

```
FAILED  a face never loses its last row (it had 1)
FAILED  and taking a row off page 2 leaves it with a way off
FAILED  and that way off goes to the page it came from
FAILED  taking a column off page 2 leaves it with one too
FAILED  and page 1 keeps the way IN to the rest
```

## 2-4 ── 設定していない2ページ目に QWERTY が出る

### **JS 側です。Swift ではありません。**

`ios/App/LinguaKeyboard/` にフォールバックはありません。`Shared.board()` は
ファイルの `lay` をそのまま使い、`KeyboardViewController.build()` は
`b.lay[min(layerNo, count-1)]` を出すだけ。**面が1つならキーボードは1面です。**
面を増やせるのは `lay` キーだけで、それを置くのはアプリです。

足していたのは `www/share.js` の `shareKbd()` です。`shareRoman()` が真のとき
`shareRomLay()` を末尾に足します ── それは**ローマ字の QWERTY 面**です。
実測（フィクスチャの言語、1面の qwerty を組んで適用）:

```
shareKbd() → { lay: 2, rom: 1 }
```

### 直した半分

`shareRoman()` は `wsys()` を聞いていました。`wsys()` は `SET.wsys` が無いとき
`wsGuess()` に落ち、**`wsGuess()` は2つの音を書く文字が1つあれば `syll` と
答えます。** つまり誰も「音節文字」を選んでいない言語に、ローマ字 QWERTY の面が
付いていました。フィクスチャの言語がまさにそれです。

`shareRoman()` は `SET.wsys` を直接聞くようになりました。**選んだときだけ。**
プランも聞きます（`SET.wsys` はプランが切れても残るので、無料に戻った言語が
変換面を送り続けないため ── `wsys()` が `can('wsys')` を聞くのと同じ理由）。

`tools/conv-check.mjs` に**9つ目の主張**。8つの主張は全部 `SET.wsys = w0` を
置いてから測っていたので、**推測されたときの道はどのチェックも一度も通って
いませんでした。** 空振りしないように、先に `wsGuess()` が変換の要る答えを
返すことを確かめてから測ります。バグを戻して**3行赤**を見ています。

### **決まっていない半分 ── オーナーへ**

**書記体系を明示的に選んだ言語では、変換面はいまも自動で足されます。**
音節文字・アブギダ・表語文字は、ローマ字で打って変換する面が要るからです
（`CLAUDE.md` rule 10 の章そのもの、`conv-check` が守っています）。

もしオーナーの言語が「音節文字」を**自分で選んだ**ものなら、**今回の直しでは
2ページ目は消えません。** 一言で決まります:

- **A. このまま** ── 変換の要る書記体系では、ローマ字面が最後に自動で付く。
  1ページ目は必ず自分のキーボード（2026-08-23 に決めたとおり）。
- **B. 自動で付けない** ── ローマ字面は自分で足すもの（ページの `＋` の
  6つ目のパターンとして「ローマ字（変換用）」を出す）。**組んだ面の数と
  実機の面の数が必ず一致します。** 変換は面を足すまで使えません。
- **C. まったく無くす** ── 変換機能ごと。`conv-check` の主張6が要らなくなり、
  音節文字は自分の文字を直接打つだけになります。

**Bを推しますが、決めません。** 一行で切り替わります。

## 4. 見つけて、直していないこと

**地球儀キーが幅を払わずに足されます。** `shareRows()` が最下行に
`{k:'next', w:1}` を差し込みますが、その行の合計を誰も数え直しません。
実機は行ごとに `幅 × w/その行の合計` で割るので、**最下行だけキーが細くなり、
列がずれます。**

```
アプリ  qwerty [10,10,10,10,10]     flick [3,3,3]
実機    qwerty [10,10,10,10,11]     flick [3,3,3,4]
```

`kbFixed()` のコメントが、まさにこのずれを直したと書いています ──
「キーボードずれた。文字サイズとか小さくしていいからずらさないで」。削除キーを
3幅にし、9文字の行に半キーの隙間を両端に置いて、どの行も 10 に揃えた、あの
作業です。**地球儀がそれを最下行だけ壊しています。無料の QWERTY も含めて
全部のキーボードです。**

直すには「地球儀の1キーぶんをどこから取るか」を決める必要があり（その行で
一番広いキー＝ふつうはスペースバー、を1つ細くする、が自然）、それは人が置いた
キーを狭めることなので、4件のどれでもありません。**`docs/BACKLOG.md` 行き**
にしていません ── この報告に書いて、リーダーの判断に委ねます。
