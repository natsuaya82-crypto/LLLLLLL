# バッジ ── オーナーが流す SQL と、そのあとの一行

「後相手の画面にパッチ映らないけど？プロなのに。そこもやってくれ」
OWNER 2026-09-04。

**一行で言うと：**`profile_seen` と `post_seen` に「プロなら真」の真偽値を
一つ足す SQL を、オーナーが Supabase のダッシュボードで流す必要があります。

---

## 1. アプリ側だけでは直せません（確かめました）

**リーダーの読み（`ME` から描かれている、作る側と読む側の線）は外れです。**

`postBadge(p)` が聞くのは `p.mine`（この投稿は自分のか）と `can('badge')`
（**自分の**プランはプロか）の二つで、どちらも読む側の話です。だから世界で
一台、書いた本人の画面にだけ出ます。線の問題ではありません ──
`tools/sides-check.mjs` は `postBadge` を既に名指しで許しています。

**アプリが他人のプランを知る道が一本もありません。**`supabase/schema.sql`
1111 行：

```sql
create policy plan_read on plan for select
  using (is_member() and id = auth.uid());
```

**自分の行しか読めません。**`profile_seen` にも `post_seen` にもプランの列は
ありません。`www/net.js` の全部の問い合わせを見ましたが、他人のプランを
答えられるものは一つもありません。**足せるデータがそもそもサーバーに
ありません。**

**投稿に焼き付けて逃げることもできません。**`tools/sides-check.mjs` に
決定が書いてあります ── バッジは凍らせない、**やめた人は外れないといけない**
「バッジは消える」。書いた瞬間に載せると、やめた後もずっと付いたままです。

---

## 2. オーナーに流してもらう SQL

**プランそのものは公開しません。**`plan` の表も `plan_read` も一文字も
変えません。「`profile` に列を置いたら全員のプランが全員に見える」という
`schema.sql` の判断は生きています。

**公開するのは真偽値ひとつだけです。**バッジは見せるためのものなので
「この人はバッジを着ているか」は公開されてよく、「何を払っているか」は
公開されません。**free と plus は同じ「偽」になります。**

VIEW は定義した人の権限で走るので `plan_read` を通らずに読めます ──
`language_seen` が非公開の言語を配らないように `where` で絞っているのと
同じ仕組みで、こちらは配る中身が真偽値ひとつです。

**流す場所：**Supabase のダッシュボード → SQL Editor → 貼って Run。
**`supabase/schema.sql` も同じ二つの VIEW を同じ形に直してください**
（この file は私の持ち場ではないので触っていません。次に schema.sql を
丸ごと流し直した日に、この直しが消えないようにするためです）。

```sql
-- ---------------------------------------------------------------------------
-- バッジ ── 「プロなら真」の一つだけを公開する
--
-- 行が無ければ偽。docs/PAID_FEATURES.md が「行が無い＝free」と書いていて、
-- 間違えるならそちら側、というのがこの file の言い分です。
-- ---------------------------------------------------------------------------

create or replace view profile_seen as
  select p.id, p.handle, p.display, p.av, p.bio, p.banned_at,
         (select count(*) from follow f where f.follower = p.id) as fo,
         (select count(*) from follow f where f.followed = p.id) as fr,
         coalesce((select pl.plan = 'pro' from plan pl where pl.id = p.id),
                  false) as pro
    from profile p;
grant select on profile_seen to anon, authenticated;

create or replace view post_seen as
  select p.id, p.author, p.language, p.prompt, p.reply_to, p.created_at,
         p.hidden_at,
         (a.banned_at is not null) as author_out,
         case when p.hidden_at is null or p.author = auth.uid() or is_staff()
              then p.body else '{}'::jsonb end as body,
         (select count(*) from react r
           where r.post = p.id and r.kind = 'like')  as likes,
         (select count(*) from react r
           where r.post = p.id and r.kind = 'boost') as boosts,
         (select count(*) from post q
           where q.reply_to = p.id and q.hidden_at is null) as replies,
         exists (select 1 from react r
                  where r.post = p.id and r.kind = 'like'
                    and r.actor = auth.uid()) as i_like,
         exists (select 1 from react r
                  where r.post = p.id and r.kind = 'boost'
                    and r.actor = auth.uid()) as i_boost,
         -- そして、書いた人がバッジを着ているか。投稿の行にあるので、
         -- タイムラインが人ごとに問い合わせを増やさずに描けます。
         coalesce((select pl.plan = 'pro' from plan pl where pl.id = p.author),
                  false) as pro
    from post p left join profile a on a.id = p.author;
grant select on post_seen to anon, authenticated;
```

### 押して確かめました

**本物の PostgreSQL に流しました。**`supabase/schema.sql` をそのまま流し、
そのうえにこの SQL を流し、A を pro・B を plus にして、**B として**読みました。

| 訊いたこと | 返ってきたもの |
|---|---|
| `profile_seen` の `pro` | `aya`（pro）= 真、`iri`（plus）= 偽 |
| `post_seen` の `pro`（A の投稿） | 真 |
| B が読める `plan` の行の数 | **1**（自分の行だけ） |

最後の行が大事です。**真偽値だけが公開され、プランそのものは今までどおり
自分の分しか読めません。**

`npm run rls` も緑のままです（この SQL は `schema.sql` を変えていないので、
そちらの 280 の攻撃は同じ結果です）。

## 3. SQL が流れたあと、アプリ側に要る直し

**SQL が流れる前に入れてはいけません。**無い列を名指しで頼むと PostgREST が
400 を返し、**タイムラインが丸ごと出なくなります。**だから今日は入れて
いません。

### `www/net.js` ── 二箇所、列名を足すだけ

1. `netWho()` の `select=` に `,pro` を足す。
2. `netFeed()` / `netPostById()` / `netFindPosts()` / `netFindPrompt` 亡きあとの
   `netReplies()` / `netPostsBy()` ── `post_seen` を読む問い合わせの
   `select=` に `,pro` を足す。**`netRow()` に一行**：
   `if(r.pro!==undefined) p.pro=!!r.pro;`

### `www/post.js` ── `postBadge()` を二行に縮める

```js
function postBadge(p){
  return (p && p.pro)? badgeMark() : '';
}
```

`p.mine` と `can('badge')` の二行が消えます。**そこにコメントで何を消せば
いいか書いてあります。**

### すでに入っていて、何も要らないもの

- `www/me.js` の `whoOf()` が `pro` を素通しします（`lid`/`lpub` と同じ形）。
- `www/me.js` の `whoCard()` が名前の横に `postBadge(p)` を描きます。
- 自分のプロフィールも `postBadge(whoOf(meHandle()))` を通ります。

つまり**相手のプロフィールは、SQL が流れて net.js の一行が入った日に、
第二の直しなしで正しくなります。**

### 検査

`tools/tl-check.mjs` が「自分の名前のバッジは Pro で付き、無料で付かない」を
持っています。**他人の分を持つ検査は、列が出来た日に足してください** ──
今は書いても、何も書き込むもののない道を試すことになります。
