```

  前   1,1,2,1,1        ← 3行目だけ 2
  後   1,1,0,1,1        ← 3行目は 0
```

**列0と列9でも2つ光っていました**（端の gap ＋ 隣の文字）。いただいた表は

## 直したところ

`kbColHas(at, w, ci)` を一箇所に置き、`kbHTML()` の判定をそれに差し替えました。

```
今:   at <= ci*2  &&  at + kbU(w) >= ci*2 + 2      （丸ごと覆う）
```

**帯（`.kbband`）は触っていません。** 列そのものを示していてキーを示しては
いないので、いただいた読みのとおりです。**帯だけ降りてキーが一つも光らない行が
出ますが、それがオーナーの言っている姿です。**

**規則19 の「列より広いキーは消さずに細くする」は無傷です。** 盤にある広いキー
3つ（`del:3` `sp:6` `ret:2`）は、どれも丸ごと覆っているので選ばれます ──
チェックが数えています。

## `kbDelCol` は同じ規則ではありませんでした

読んで確かめました:

```js
cut = Math.min(at+u, b) - Math.max(at, a);   // 交差の長さ
if(cut>0) u -= cut;                           // その分だけ細くする
```

**これは「このキーは何列ぶん削られるか」という長さの計算で、「このキーはこの列で
出来ているか」という可否ではありません。** 二つの別の問いなので、一箇所に
まとめていません ── `CLAUDE.md`「繰り返しが全部重複なわけではない」。

**そして削除は効き続けるべきです。** もし削除も「丸ごと覆うものだけ」にすると、
食い込んだ行だけ列1つ分短くならず、他の行と揃わなくなります。オーナーの原文も
削除が効く前提です（「削除して中央揃えした場合…」）。

`kbColHas()` の隣と `CLAUDE.md` rule 19 に、その二つが別の問いだと書きました
（次に読む人が「一箇所にまとめよう」としないように）。

## 見つけて、直していないこと ── `docs/BACKLOG.md` に入れました

**列を消すと、文字キーが幅0.5 で残ることがあります。**

```
前   gap:0.5  lt:1  ... lt:1  gap:0.5
後   lt:0.5   lt:1  ... lt:1  gap:0.5      ← 390pt 端末で 14pt
```

**半分しか掛かっていないキーは選ばれなくなったのに、削除では削られます。**
矛盾ではなく二つの別の問いですが、**押せない幅のキーが生まれます。**
`press` は捕まえません ── キーボードのキーは高さだけで 44pt を測るからで、
それは rule 19 が決めたことです（幅の下限はどこにもありません）。

**オーナーの判断が要ります**（今のまま／丸ごと残す／丸ごと消す）。BACKLOG に
三つの代金を書いてあります。

**なお「削除して中央揃えした場合全部がハンキーになる」は、文字どおりには
起きません。** 半キーになるのは先頭の1つだけで、中央寄せしても動きません
（行の合計が揃っていて余りが無いため）。実測です。
