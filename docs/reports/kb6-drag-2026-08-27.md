## 何が既にあるか

`master` の `www/keyboard.js`:

| | |
|---|---|
| `kbDown()` | 指が触れた瞬間。**380ms** のタイマーを置く |
| `kbLift()` | 380ms 経ったら発火。キーが浮き、`kbWob=true`（ホーム画面と同じ、全キーが揺れる状態） |
| `kbDragTo()` | 指の下のキーを `elementFromPoint` で探し、`insertBefore` で**行をまたいで**入れ替える |
| `kbUp()` | 離した瞬間。`kbReadRows()` が画面から並びを読み戻し、`saveKb()` |

コメントも既にそう言っています ──
「長押ししたら右上に➖出てきて消える。iPhoneのホーム画面と同じ挙動」
「長押しして持っていきたいのに動かない」（これは直された跡です）。

### 測り方

`tools/kb-check.mjs` と同じ立ち上げ方で本物のアプリを起動し、**本物の
`kbDown` / `kbLift` / `kbDragTo` / `kbUp` を呼びました。** 指が無いので
`document.elementFromPoint` だけ、「指の下にあるのは何か」という**一問のあいだ
だけ**差し替えています。それ以外は全部アプリのコードです。

## ① 今の画面の習わしに乗るのか ── **乗っています。既に同居しています**

心配されている「掴んで動かすのは、行の番号・列の文字で選ぶのと別の入り方では
ないか」は、**もう解かれています。**

キーの `[data-do]`（＝タップで選ぶ）を測りました:

| | キーに `data-do` があるか |
|---|---|
| 普通のとき | **ある**（`kbTapKey` ＝ 押して選ぶ） |
| 揺れているとき（長押し後） | **ない** |

`kbKeyHTML` が `(kbWob? '' : DO('kbTapKey', [ri, ki]))` と書いているからです。
**揺れているあいだ、タップは存在しません。** さらに `kbUp()` は動かした場合に
`preventDefault()` を呼ぶので、**運んだ指がそのままキーの画面を開くこともありません。**

選択（`KBH`）と運搬はぶつかっていません。二つの入り方が一つの画面に同居する形は、
既に決着済みです。

## ② 動かした先が埋まっていたら ── **割り込んで、行が十を超えていました。直しました**

**②の案とは無関係に、この日の `master` にあったバグです。** 以下は見つけたときの
測定で、直したあとの話は §「決まりました」から。

qwerty パターンの盤（各行ちょうど十キー）で、行1のキーを行0へ運びました。
数字は**半列**（十キー = 20）です:

```
運ぶ前   [20, 20, 20, 20, 20]     全部ちょうど十キー
運んだ後 [22, 18, 20, 20, 20]     行0が **十一キー**
```

`kbDragTo()` は `row.insertBefore()` するだけで、**行の幅を一度も訊きません。**

**訊く関数は在ります。** `kbRoomIn()` ── 手で足すとき（`kbCellAdd`）は
これを通っていて、満杯の行には入りません。運搬だけがそれを通っていません。

規則19 は「**十が電話の数**」と言っています（一番細い iPhone が320なので
十キーで32ずつ、十一なら29）。運搬はその天井の**外**にいます。同じことは
`kb5` 側でも測りました ── 同じ数字が出ます。**`kb5` が入れたものではありません。**

### 決まりました ── **A（拒む）。入れました**

> 「満杯だと追加できないから」 **OWNER 2026-08-27**

出した四択のうち **A** です。**理由がそのまま決定の言葉になっています** ──
手で足すとき（`kbCellAdd`）は `kbRoomIn()` を通って満杯の行に入らないので、
運搬も同じ扱いにする、ということです。

| | 何が起きるか | |
|---|---|---|
| **A 拒む** | 満杯の行には落ちない。指を離すと元の場所 | **これになりました** |
| **B 入れ替える** | 落ちた先のキーと場所を交換する | 採られませんでした |
| **C 押しのける** | あふれた分を次の行へ送る | 触っていない行が動くので不採用 |
| **D 今のまま** | 十一キーの行ができる | 規則19が禁じている数そのもの |

**私は B を推していました。採られたのは A です。** 私が挙げた A の唯一の心配
（「動かない」と読まれる）は残りますが、手で足すときと同じ振る舞いになるので、
この画面の中では一貫します。**演出は何も足していません**（アプリ内に説明は禁止）。

#### 押し返されたことは目で分かるか ── **実測しました。分かります**

リーダーに「分からないなら測って報告」と言われたので、断られた運搬と入った運搬を
並べて測りました。`transform` と、親（行）が変わったかどうか:

| | 運んでいる間 | 指を離すと |
|---|---|---|
| **断られた** | `transform: translate(50px, 90px)` ── **指について来る**。ただし行は変わらない | transform が消えて**元の場所へ戻る** |
| **入った** | `transform` は無し、**親の行が変わっている** ── その場に**収まる** | そのまま |

つまり、入った運搬は指の下で**キーが行にはまって止まり**、断られた運搬は
**はまらずに指について来続け、離すと戻ります。** 二つは見た目が違います
── iPhone のホーム画面でアイコンを詰まった所へ持っていったときと同じ形で、
**何も付け足さずにそうなっています。**

#### 入れたもの

`kbDragTo()` が `kbRoomFor()`（`kbRoomIn()` と同じ規則）を訊きます。
**行をまたぐときだけ** ── 同じ行の中は幅が変わらないので、訊くとキーを二度数えて
満杯の行の並べ替えが凍ります（これも赤で確かめました）。

`kb-check` に六項目。**特に二つ「どの行も十以下」と「キーは元の場所に戻っている」
は分けてあります** ── 断るときにキーを**消す**バグを入れると、
**前者は緑のまま**（10, 9, 10, 10, 10）で、捕まえたのは後者だけでした。

## ③ 結合キー（`h` と `up` の対）を動かすと ── **黙って結合が外れます**

`kb5` の縦結合を読み込んだ木で測りました（`master` にはまだ `kbVJoin` が
無いので、そちらでは起きません）。

結合直後の1行目・2行目:

```
行0   lt::1:h2  lt::1  lt::1 ...       ← 上のキーが h=2（二行ぶんの高さ）
行1   gap::1:up lt::1  lt::1 ...       ← 下は「影」の gap、up=1
```

**上半分（背の高い方）を別の行へ運んだ後:**

```
行0   lt::1 lt::1 ...                  ← h2 が **消えている**
行1   gap::1 lt::1 ...                 ← up も **消えている**
```

`h2` も `up` も残っていません。**下半分は一緒に動きません。**

**外しているのは `kbVFix()` です。** `saveKb()` から走り、対が縦に揃って
いなければ `delete k.h` / `delete k.up` します ── そういう設計です（「Merges,
kept honest, in one place」）。運搬は `kbReadRows()` → `saveKb()` で終わるので、
**運んだ瞬間に `kbVFix()` が「この対は壊れている」と判断して、直す代わりに
ほどきます。**

これは `kbVFix()` のバグではありません。**運搬が `kbVFix()` に「対が動いた」と
言う手段を持っていない**だけです。何も throw せず、画面は正しく描かれ、
**結合だけが無かったことになります。**

**オーナーの決定が要ります:** 結合したキーを長押しで掴んだとき、

- **一緒に動く**（対のまま運ぶ。落ちる先も二行ぶん要る ── 一番下の行には落ちない）
- **掴めない**（結合しているあいだは運搬の対象外。ほどいてから動かす）
- **今のまま**（黙ってほどける ── **これは選ばれるべきではないと思います**。
  人が作ったものが、警告なしに消える形なので）

## ④ 巻き戻しに乗るか ── **乗ります**

`kbReadRows()` が `saveKb()` で終わり、`saveKb()` が `kbNoted()` を呼ぶので、
運搬は一手として記録されます。測りました:

```
運ぶ前   [20, 20, 20, 20, 20]
運んだ後 [22, 18, 20, 20, 20]
巻き戻し [20, 20, 20, 20, 20]     ← 幅まで完全に元通り
```

**上の②③をどう決めても、取り消しは効きます。** これは既にある財産です。

## ⑤ `press` は何を検査できて、何ができないか ── **正直に**

**`press` はこれを一度も押していません。押せません。**

`press` は `[data-do]` を持つ要素に `click()` を投げる walk です。運搬は

| | |
|---|---|
| `press` が押さえているもの | タップで選ぶ側（`kbTapKey`）が throw しないこと、画面が空にならないこと |
| `press` が押さえていないもの | **長押しも、運搬も、落とす先も、幅も、結合も、一つも** |

`kb-check` も今は運搬を一項目も持っていません（`fresh()` からの盤に対して
行・列・幅・面・巻き戻しを見ています）。

**書きました。** 満杯の行に落とさない決定が来たので、`kb-check` が
本物の `kbDown` / `kbLift` / `kbDragTo` / `kbUp` を、この報告の数字を出したのと

## 入れるなら、この差分です（測って書いています、入れていません）

**`www/sound.js`** ── `ltSort` / `ltFil` の隣（699行あたり）:

```js
var ltQ='';
function ltSetQ(v){ ltQ=String(v||''); ltPaint(); }
function ltQList(list){
  if(!ltQ) return list;
  var q=ltQ.toLowerCase();
  return list.filter(function(l){
    return String(ltName(l)||'').toLowerCase().indexOf(q)>=0;
  });

```

`indexOf(...)>=0` であって `.includes` ではありません（規則1）。

**`ltViewRow()` に、`.search` を一つ。** `index.html` の既存のもので、
新しい CSS は要りません ── `ipaPickHTML()` が同じ形を既に使っています:

```js
'<div class="search"><span class="lens">'+ICON_LENS+'</span>'+
  '<input id="lt-q" value="'+esc(ltQ)+'"' + IN('ltSetQ') + '></div>'
```

**`render()` ではなく部分描画が要ります。** ここは実測ではなく既存コードの
形からの指摘ですが、根拠があります: `ipaSetQ()` は `render()` を呼ばず
`ipaPaint()` で `#ipa-list` の中身だけ描き直します。**一文字打つたびに
`render()` すると入力欄そのものが作り直され、focus とカーソルが飛びます。**
だから `ltPaint()` も同じ形（grid に id を振って `innerHTML` だけ差し替え）に
なります。**そしてそれは、二つの画面が同じ関数を呼ぶ理由の三つ目です。**

**一覧を通す所** ── `vLtset` と `kbLtGrid` の両方が、今の
`ltFilList(ltSortList(...))` を `ltQList(ltFilList(ltSortList(...)))` にします。
`kbLtGrid` の側は**私の持ち物なので、私が入れられます。**
