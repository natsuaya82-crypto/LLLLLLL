## 4. 消した単語・文字・ノートが、次に電波の届いた起動で戻ってくる

**一番危ないのはこれです。**

**何が起きるか。**
辞書から単語を一つ消して、「削除しました」と出て、一覧から消えます。
アプリを閉じて、次に電波のある所で開くと、**その単語が一覧の一番下に戻っています。**
文字も、ノートも、文法の項目も同じです。消した単語を使っていた例文も一緒に戻ります。

戻ってくるのは**位置も違います** ── 元の場所ではなく、一覧の末尾です。
そして戻った単語を指していた `from` `syn` `ant` の繋がりは切られたままなので、
**半分だけ戻った形**になります。

**なぜそうなるか。**
消したことがサーバーに一度も伝わりません。スライスをサーバーへ送る所は
`www/net.js:1450` の一箇所だけで、そこが送るのは**必ず合成した後のもの**です。
合成（`www/sync.js:56` `syArr()`）は**足すだけ**なので、
サーバーが持っている「消す前の一覧」がそのまま自分の側へ戻り、
戻ったものが今度はサーバーへ書き戻されます。**スライスは、どちらの側でも
短くなれません。**

**どこにあるか。**

| | |
|---|---|
| `www/wordsheet.js:1580` | `delWordGo()` → `wDrop()` → `save()`。`save()` は `localStorage` にしか書かない |
| `www/net.js:1222` | `netSlicePut()` ── サーバーへ送る唯一の関数 |
| `www/net.js:1450` | その唯一の呼び手。渡すのは `syMerge()` の結果 |
| `www/sync.js:56` | `syArr()` ── 自分の側、次に相手の側。落とすのは重複だけ |
| `www/letters.js:1027` | `ltDel()` ── 文字も同じ道 |

**確かめたこと（走らせて）。**`www/sync.js` は DOM も globals も使わないので、
そのまま Node で走らせました:

```
消した後の辞書 : [{"hw":"aka"},{"hw":"telo"}]
合成して書く方 : [{"hw":"aka"},{"hw":"telo"},{"hw":"sina"}]
sina は戻るか   : true
文字 l2 は戻るか: true
ノートは戻るか  : true
```

**確かめていないこと。**実機では押していません。上は `syMerge()` 単体を
走らせたもので、起動から画面までを通したものではありません。

**検査は一本も見ていません。**`tools/again-check.mjs` は逆向きだけを押さえて
います ──「二度同期しても辞書が増えないこと」「小さくなって返ってきたら拒む
こと」。**「消したものが消えたままか」を訊く検査は一つもありません。**

**書いた仕様はあるか。** ありません。`docs/FEATURES.md:325` と `:591` は
「代償は重複であって削除ではない」と、**足すことの良い面としてだけ**書いています。
`docs/FEATURES.md:518` は**言語まるごと**を消す場合について「iPhone だけで消すと
次の同期で戻る」と正しく書いてあり、だから言語の削除はサーバーの行を先に消します。
**単語一つ・文字一つには、その半分がありません。**

**どれくらい起きやすいか。** いつも（サインインしていて、その言語がサーバーに
在って、電波がある場合）。

**直す大きさ:** 中。**どう直すかはオーナーの決めごとです** ── 消したことを
記録して送るのか、その一つのスライスだけは上書きにするのか、二つ以上の道があり、
どちらも `docs/DATA_SAFETY.md` に触ります。

## 5. 同じ投稿が、サーバーに何度も上がる

> **直りました ── 2026-09-04、`claude/post3`。**
> `POST_SENDING` と `postSend()`（`www/post.js`）。いまワイヤに乗っている
> 投稿を、この iPhone 自身の id で憶えて、送っている間は二度目を断ります。
> **押した側（`pwSendWith`）も窓の半分でした** ── 押して、写真が上がって
> いる最中にタイムラインの返事が来る ── ので、両方の道を一つの関数に
> 通しました。投稿には書きません: 保存される印は送信の途中でアプリが
> 落ちたときに生き残り、その投稿が二度と送られなくなります。
> 押さえているのは `post-check` の 15 番。**実機では押していません。**


**何が起きるか。**
電波の悪い所で写真の付いた投稿を出し、そのままタイムラインを見ていると、
**同じ投稿が二つ、三つと並びます。**自分の画面にも、他の人の画面にも並びます。
消すには一つずつ消すことになります。

**なぜそうなるか。**
まだサーバーに行っていない投稿を送り直す `postCatchUp()`（`www/post.js:1047`）に、
**「いま送っている最中」という印がありません。**見ているのは
`if(ps[i].sid || ps[i].pv || !ps[i].mine) continue;`（`www/post.js:1052`）── 
`sid` はサーバーが返事をして初めて付きます。

`postCatchUp()` はタイムラインの返事が来るたびに走ります
（`www/sns.js:327`）。そしてタイムラインは**画面を描くたびに**訊きに行きます
（`vFeed()` が `snsPull()` を呼ぶ）。写真の付いた投稿を送るのは
`netUpPics()`（`www/net.js:2570`）で、写真を一枚ずつ順番に上げるので**秒がかかり
ます。**その間にタイムラインの返事は何度も返ってきます。返ってくるたびに、
まだ `sid` の付いていない同じ投稿が、**新しい id で**もう一度送られます
（`netPush()` は毎回 `pid=netUUID()` を作ります、`www/net.js:2638`）。

**どこにあるか。** `www/post.js:1047-1058`、`www/sns.js:313-327`、
`www/net.js:2635`。

**確かめたこと。** ソースを読みました。`postCatchUp()` に送信中の印が無いこと、
`snsPulling` が押さえているのは `netFeed` だけで `netPush` ではないこと、
`netPush` が毎回新しい id を作ることを確認しました。

**確かめていないこと。実機で押していません。**上は道が二本以上あることを
読んで言っているもので、実際に二つ並ぶのを**見てはいません。**

**どれくらい起きやすいか。** 写真の付いた投稿を電波の悪い所で出したとき。
写真の無い投稿でも道は同じですが、窓が短いので起きにくいはずです。

**直す大きさ:** 小（送っている間の印を一つ）。

## 6. 投稿の写真と声が黙って落ち、二度と上がらない

> **直りました ── 2026-09-04、`claude/post3`。ただし片方は決めごとです。**
> `netUpPics()` と `netUpVoice()`（`www/net.js`）が、上がったパスを投稿に
> 書きます（`pu[i]` `pt[i]` `vu`）。既に上がっているものは二度送りません。
> **そして行は、バイトが揃ってから出します。**断られた状態は、トンネルで
> 書いた投稿と同じ状態 ── 行が無く、`sid` が無く、投稿はバイトを持ったまま
> `POSTS` に座り、次のタイムラインの返事で `postCatchUp()` がもう一度
> 試します。二度目は足りない一枚だけです。何も落としません。
>
> **同じパスへは送り直せません。**`supabase/schema.sql` のバケツには
> update の方針がわざと在りません（「an overwrite is how somebody else's
> post quietly changes under them」）。だから二度目は二度目自身の
> フォルダへ行き、投稿が持っているパスが二つのフォルダを繋ぎます。
> 置き去りは出ません ── `netDropFiles()` はフォルダではなく投稿の持つ
> パスで消すので。
>
> **選ばなかった方: 行は今まで通り出して、落ちたことを持ち帰り、
> あとから PATCH で仕上げる。**そちらは道が一本増えます（PATCH と、
> 行が未完成だと言う印）。選んだ方は道を一本も増やしません。
> **オーナーが逆を選ぶなら、戻すのは `netPush()` の中の二行です。**
>
> 押さえているのは `post-check` の 16 番。**実機では押していません。**


**何が起きるか。**
写真を四枚付けて投稿すると、**自分の画面には四枚出ます。**
他の人の画面には三枚しか出ないことがあります。声も同じで、
**自分の iPhone では再生でき、他の人には何も付いていない投稿に見えます。**
何も言われず、あとから直る道もありません。

**なぜそうなるか。**
一枚ずつ上げていて、上がらなかった一枚の失敗の受け口が空です:

- `www/net.js:2590` ── 写真が上がらなかったとき `function(){ next(); }`。
  そのまま次の一枚へ進み、**その一枚は一覧から落ちます。**
- `www/net.js:2679-2680` ── 声が上がらなかったとき `ok('')`。
  声の道が付かないまま投稿が送られます。

そして投稿の行そのものは送られ、成功として `sid` が付きます
（`www/net.js:2666`）。`sid` が付いた投稿は `postCatchUp()` が二度と触らないので
（`www/post.js:1052`）、**落ちた写真と声は永久に上がりません。**

自分の側に残るのは、投稿の写しが `pics` と `vo` を base64 で持っているからです
（`netBody()` が `www/net.js` でその二つを送らない ── それは正しい）。
**だから自分だけが正しく見えます。**`CLAUDE.md` §「The making side and the
reading side are separate」が名指ししている
「it tests green, screenshots right and demos perfectly, and the day the second
person arrives」がこの形です。

**どこにあるか。** `www/net.js:2570-2593`（写真）、`www/net.js:2674-2682`（声）、
`www/net.js:2635-2668`（投稿の行）。

**確かめたこと。** ソースを読みました。**押していません。**

**確かめていないこと。**`netUp()` がどういうときに失敗を返すか（大きさの上限、
待ち時間）は見ていません。`aud-reject.md` が「通信に `timeout` が無い」と
書いているのと同じ場所です。

**どれくらい起きやすいか。** 上がらなかったときは、いつも黙ります。
何回に一回上がらないかは分かりません。

**直す大きさ:** 中（落ちたことを持って帰るのか、投稿ごと止めるのかは決めごと）。

## 7. 検索履歴が「消してから入れ直す」形で、途中で切れると消える

**何が起きるか。**
一度検索した言葉をもう一度検索すると、履歴の一番上へ動きます。その動かし方が
**「消す」→「入れる」の二回**で、間で電波が切れると**消えたまま**になります。

## 8. 起動の同じ瞬間に、言語を降ろす道と上げる道が両方走る

**何が起きるか。**
一つの言語が、一覧に**二つ**並ぶことがあります。中身は同じです。

**なぜそうなるか。**
`www/boot.js:102` の `netLangsDown()` と `:110` の `netLangSync()` は、
同じ瞬間に投げられ、どちらも待たれません。`netLangsDown()` は
**関数の頭で**「この iPhone が既に持っているサーバーの行」を控えます
（`www/net.js:1270-1272`）。その控えを取った後で `netLangSync()` が
新しい行を作り（`netLangRow()`、`www/net.js:984`）、
その行がサーバーの返事に載って戻ってくると、控えに無いので
**「この iPhone がまだ持っていない言語」として、もう一つ作られます。**

扉の側にも同じ組があります ── `obIn()` が `netLangsDown()` を呼び
（`www/onboard.js:880`）、`obFinish()` が `netLangSync()` を呼びます
（`www/onboard.js:1817`）。

**確かめたこと。** ソースを読みました。**押していません。**

**確かめていないこと。**GET が先に投げられているので、普通は GET が先に返ります。
**実際にこの順が入れ替わるのを見てはいません。**

**どれくらい起きやすいか。** まれ。**その言語が初めてサーバーへ上がる一回だけ**
（二回目からは `sid` が控えに入ります）。

**直す大きさ:** 小（`netLangsDown()` の後で `netLangSync()` を呼ぶ）。

## 9. 消した投稿の写真が、上がらなかった場合に公開のまま残る

> **半分直りました ── 2026-09-04、`claude/post3`。**
> `NET_DROPLEFT` と `netDropAgain()`（`www/net.js`）。人が既に「消して」と
> 言い、ワイヤが断ったファイルのパスを持ち帰り、次に通信が動いていると
> 分かる瞬間（`postCatchUp()` が使っているのと同じ瞬間）にまとめて出し
> 直します。断られ続けたらリストはそのまま残り、次のタイムラインでまた
> 試します ── ここで諦めることはしません。
> **掃除でも間引きでもありません。**その投稿が名指ししていたファイルだけで、
> `docs/CHANGELOG.md` の DELETE REVIEW が許している範囲そのものです。
>
> **残っている穴 ── リストはメモリの中だけです。**断られた直後にアプリを
> 落とすと、どのファイルを追うべきかを忘れます。塞ぐには置き場所が要ります
> ── 端末の鍵（`tools/store-check.mjs` が持ち主）か、サーバーの行
> （`supabase/schema.sql` が持ち主）── **どちらもこのセッションの持ち物では
> ありません。**そして何日置いてよいかは保存期間の話で、**オーナーのもの
> です。**
>
> 押さえているのは `post-check` の 17 番。**実機では押していません。**


**何が起きるか。**
投稿を消すと、写真と声のファイルを先に消してから行を消します。
**ファイルが消せなくても、行は消します。**そのときファイルは公開バケットに
残り、誰も指していないので**もう誰にも見つけられず、消す道もありません。**
URL を知っている人には、そのまま見えます。

**どこにあるか。** `www/net.js:2799-2801`（`netDropFiles()` の失敗の受け口が
`function(){ done(); }`）。バケットが公開であることは `www/net.js:2390`
（`/storage/v1/object/public/post-media/`）と、`www/net.js:2694` の注。

**これは半分わざとです。**`www/net.js:2770` の注が
「If the files will not go the row still does: a post somebody asked to be gone
must go」と書いています。**書かれていないのは、残った側が公開のままだという
ことと、後から拾う道が無いことです。**

**確かめたこと。** ソースを読みました。**押していません。**

**どれくらい起きやすい か。** ファイルの削除が失敗したときだけ。
URL は uuid 二つなので、当てずっぽうでは届きません。

**直す大きさ:** 中（残ったものを記録する所が要る。運営側の話でもある）。
