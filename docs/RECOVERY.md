# バグで消えたときに、運営側で戻すための案

「あとバグとかで人のデータが消えた時に運営側で復旧できる要素が欲しい」
「バグが多すぎて、セーフティーネットを作らないと炎上するだろ」
「復旧は自分で消した時じゃなくてバグで消えた時の話な」 OWNER 2026-09-03

**案A は採られ、入りました**（2026-09-04、`claude/rec2`）。四章の案A に、何が
入って何が入らなかったかを書いてあります。**案B と案C はまだ案のままで、
コードは一行もありません。**

**残す期間は決まっていません。**オーナーがまだ答えていません。**古い版を消す
仕組みは作っていません** ── 自動削除は禁止です（`docs/DATA_SAFETY.md`）。
期間が決まってから、別の仕事として作ります。ここには「期間によって何が
変わるか」を書きます。

**線引き。**戻すのは**バグで消えたとき**だけです。本人が消したものは戻しません。

## 二、今すでにあるもの

**新しく作る前に、あるものを数えました。八つあります。**

1. **`keep()` は最後の無事なファイルを壊さない**（`LinguaShare.swift:140`）。
   `.tmp` に書く → 読み直して JSON として通るか見る → そこで初めて世代を回す。
   書き損じは一世代で済み、人の何か月分は失われません。
2. **`bkTake()` は「無い」ものだけ埋める**（`www/backup.js`）。有るスライスには
   触りません。復元が勝つことでデータが死ぬ、という形を塞いでいます。
3. **`bkSound()` は「空」と「壊れている」を分ける**（`BK_SHAPE` と照合）。
   `[[[not json` は「有る」ので昔は素通りしていました。今は壊れているものは
   ファイルに書き出しません。
4. **`syMerge()` は両方足す**（`www/sync.js`）。どちらが新しいかを決めません。
   代償は重複で、重複は画面に出るので直せます。
5. **`netKeeps()` は縮む書き込みを断る**（`www/net.js`）。マージの結果が
   今あるものを含んでいなければ localStorage に書かず、`NET_SHRANK` に控えます。
6. **`netLangsDown()` / `draftsPull()` も「無いものを埋めて止まる」**。
7. **`bkDropFor(ids)` は名指しでしか消せない**。2026-09-03 に
   「フォルダを空にする」道が二つとも削除されました。
8. **`tools/del-check.mjs` が消す口を全部数えている。**削除に見える名前の act は
   **33 個**、そのうち**ストレージから何かを取るものは 21 個**、
   取らないものは 12 個。新しい口は理由を書くまで赤になります。

### 足りないのはどこか

**`slice` の穴は塞がりました**（案A、下）。**残りは塞がっていません。**

- ~~`slice` は upsert で上書きされ、前の中身は消えます~~ ── **`slice_past` に
  残るようになりました。**`slice` の `body` が書き換わる直前の中身が、
  `slice_keep` トリガで一行として控えられます。言語一本につきサーバーの版が
  常に一つ、という状態は終わりました。
- `post` と `draft` は今も update で上書き、delete で消えます。行の履歴は
  ありません。**ここは案B の領分で、まだ何もありません。**
- `publication` だけが追記専用ですが、**入っているのは sha-256 の指紋だけ**で、
  中身ではありません。「これは自分が先に作った」を示す証拠にはなりますが、
  戻すのには使えません。
- **バケツのバイトには履歴も版もありません。**削除は即、永久です。
- Supabase 側のバックアップ設定（PITR など）は `supabase/setup.md` に
  一言も書かれていません。**入っているかどうかは未確認です。**

そして、**運営側から人のデータを見る道が今は一つもありません。**

## 三、消え方の種類

**このコードで実際に起こりうるものだけ**書きます。思いつきは並べません。
どれも「読んで確認した」か「走らせて確認した」かを添えます。

### 1. iPhone の中の壊れた一本が、サーバーの無事な一本を上書きする　【走らせて確認】

`syMerge()` は、どちらかが JSON として読めないと **iPhone の側を返します**。
`netLangSync1()` はそれをそのまま `netSlicePut()` に渡します。

```
iPhone の words = [[[not json    サーバーの words = 単語 3000 個
   → syMerge は iPhone の壊れた文字列を返す
   → netKeeps(mine, put) は put===mine なので通る（そもそも比較にかからない）
   → put !== サーバーの body なので netSlicePut が飛ぶ
   → サーバーの 3000 語が [[[not json になる
```

`www/sync.js` と `www/net.js` の `netKeeps` を抜き出して走らせ、この四行が
そのとおりになることを確認しました。**バックアップファイルの側は
`bkOK()` が断るので壊れません**（`bkPush()`）が、サーバーには断る所がありません。
`bkSound()` は同期の道では一度も呼ばれていません。

**これが一番危ない道でした。**iPhone のストレージが一本壊れるだけで、
サーバーの唯一の版が消えていました。**案A が入って、消える直前の版は
`slice_past` に残るようになりました。**上がってくるのを止める仕組みでは
ありません ── **上書きは今も起きます。戻せるようになっただけです。**

### 2. 保存が黙って失敗する　【読んで確認・押していない】

`www/core.js:512` の `save()` は全体が `try{ … }catch(e){}` です。
localStorage が満杯、あるいは書き込みを拒否されたとき、**単語も行も名前も
`script` も設定も索引も、一つも書かれず、画面には何も出ません。**
`bkTouch()` は先に走っているのでバックアップは書かれますが、`bkPack()` は
localStorage を読むので、**書けなかった古い中身が書き出されます。**
`langStore()` も同じ形です（`www/core.js:184`）。

`savePosts()` だけは違い、失敗すると `toast(t('post.full'))` を出します。

### 3. 言語が「誰のものでもない」になって、消えていないのに全部から外れる　【読んで確認】

`LANGS[id].uid` が落ちるか、`mine` が false になると:

- `langOwned()` が false ── 一覧に出ない
- `langMineIds()` に入らない ── **同期されない**（上がりも下りもしない）
- `bkPush()` が `langMine()` で断る ── **バックアップファイルにも書かれない**

localStorage には全部残っているのに、見えず、守られません。
`bkTake()` のコメントがこの形を書いています ── 復元した言語に印を押さなかった
ために、`lingua.<id>.*` に一語も欠けずに入っているのに、どの一覧にも
どの数にも出なかった、と。**過去に実際に起きた形です。**

### 4. 索引だけ消えて、スライスが孤児になる　【読んで確認】

`langStore()` が失敗する（上の 2）と、`LANGS` の行が無いままスライスだけが
`lingua.<id>.<slice>` に残ります。索引に無い言語は誰も名前を言えないので、
バックアップにも同期にも入りません。サーバーに一度でも上がっていれば
`netLangsDown()` が拾い直しますが、**`sid` が無い言語 ── 一度も上がって
いない言語 ── は拾えません。**

### 5. 片方だけ消える　【読んで確認】

投稿の削除（`postDel`）は、サーバーの行・バケツのバイト・iPhone の写し・
`Documents/Voices/` のファイルを順に片付けます。途中で通信が切れれば
片方だけ消えます。言語の削除（`wipeLangsGo`）は `netLangDrop(id)` を
**待ちません** ── iPhone からは消えて、サーバーの行が残ることがあります。

### 6. 一つのアカウントの削除が、別のアカウントのものを持っていく　【起きた】

2026-09-03 に実際に起きました。`lsWipeNS()` が `lingua.` で始まるキーを
全部持っていき、`bkDropAll()` が Languages フォルダを空にしていたので、
**二つ目のアカウントを消したら一つ目のアカウントの言語が消えました。**
その言語は一度もサーバーに上がっておらず、iPhone が唯一の写しを自分で壊しました。

**両方の関数は削除済みです**（`lsWipeAcct(uid)` と `bkDropFor(ids)` になった）。
ここに書くのは、**これが「バグで消えた」の実例であり、そして今の仕組みでは
一つも戻せなかったから**です。

### 7. サーバーの一行を、間違った中身で上書きする　【読んで確認】

1 の特別な場合だけではありません。`slice` は上書きの表です。マージの結果が
何であれ、`netSlicePut()` が飛べばサーバーの版は置き換わります。
**案A が入って、置き換わる直前の版は `slice_past` に残ります。**
置き換わること自体は変わっていません。

三つあります。**案A は入りました。案B と案C はまだ案で、コードは一行も

期間はどれも「オーナーが決める」です。案ごとに、期間で何が変わるかを書きます。

### 案A ── サーバーで、スライスの前の版を残す　【採られました。入っています】

**2026-09-04、`claude/rec2` で入りました。**`supabase/schema.sql` だけの変更で、
**アプリ（`www/`）は一行も変わっていません。**手順は
`supabase/setup.md` § 11 にあります。

**なぜこれが選ばれたか:** 一番失って困るもの（何か月分の言語）が、サーバーに
**一つしか版が無く、保存のたびに上書きされる**から。そこに履歴を付ければ、
上の消え方 1・7 は戻せます。

**何が入ったか**

`slice` の `body` が書き換わる直前の中身が、別の表に一行として残ります。

```
slice_past(id, language, kind, body, no, at, kept_at)
```

- **`slice_keep`** ── `slice` の BEFORE UPDATE トリガ一本。中身が**本当に
  変わったときだけ**控えます。同じ文字列が二度届いても行は増えません。
  アプリの upsert（`Prefer: resolution=merge-duplicates`）でも発火します。
- **`kept_at`** は**このサーバーの時計**で、並べ替えはこれでやります。
  `at` は端末が送ってきた時刻なので、ずれていることがあります
  （`docs/DATA_SAFETY.md` § 保存の通し番号と同じ理由）。
- **読めるのは本人と運営（@lingua）だけ**です。`is_admin()` ── 管理画面と
  同じ問い ── で、新しい決め方は作っていません。**公開した言語でも、その
  過去の中身は他人から一行も見えません。**スタッフも読めません。
- **誰も書けません。**insert / update / delete のポリシーが一つも無いので、
  API からは一行も足せず、直せず、消せません（`publication` と同じ形）。
  書くのはトリガだけです。

**調べて戻す道**

`supabase/setup.md` § 11 に、**そのまま貼って動く SQL** が五つ並んでいます ──
その人の言語を見つける → いま何が入っているかを見る → 前の版を並べる →
選んだ一行を戻す → 戻ったか確かめる。ダッシュボードの SQL エディタで押します。
**画面は作っていません**（`www/` は触っていません）。

戻す文は `slice_past` の行から言語と種類を読み直すので、**版の数字を打ち
間違えても別人の言語には届きません。**そして**戻す操作そのものも控えられる**
ので、間違った版を戻しても同じ手順でやり直せます。

**量の見立て ── オーナーが期間を決める材料**

`netLangSync1()` は、マージの結果がサーバーの `body` と同じなら送りません
（`put===got.body` で止まる）。**中身が本当に変わったときだけ一行増えます。**
無料の言語まるごとで約 25 KB、5000 語で約 685 KB（`docs/DATA_SAFETY.md` の
実測）。ただし `words` を一語足すたびに、**その時点の `words` 全部**が一行と
して残ります ── **保存一回ごとに、その言語の今の大きさぶん**です。

| 一人が一日に保存する回数 | 言語の大きさ | 一日に積まれる量 | 30 日 | 365 日 |
|---|---|---|---|---|
| 20 回 | 25 KB（無料・38 文字と少しの単語） | 0.5 MB | 15 MB | 183 MB |
| 20 回 | 685 KB（5000 語） | 13.7 MB | 411 MB | 5.0 GB |
| 100 回 | 685 KB（5000 語） | 68.5 MB | 2.1 GB | 25 GB |

**一人あたりです。**使っている人の数を知らないので、全体の見立ては書きません。
**「一日 20 回」も仮の数字で、測っていません。**表の読み方は「大きい言語を
毎日書く人が一人増えると、一年でこれくらい」です。

- **短い（例: 数日）** ── 直近のバグは戻せる。オーナーが気づく前に流れる
  可能性がある。置き場は小さい。
- **長い（例: 数か月）** ── 「先月から単語が減っている」に答えられる。
  大きい言語を毎日書く人が増えると置き場が効いてくる。

**期間はまだ決まっていません。古い行を消す仕組みは作っていません。**
自動削除は禁止です（`docs/DATA_SAFETY.md`）。`npm run rls` に
「このファイルの中に `slice_past` から消すものは一つも無い」という行があり、
**期間が決まった日に、その行を DELETE REVIEW と一緒に外すことになります。**

**この案で守れないもの**

- **サーバーに一度も上がっていない言語。**`sid` が付く前 ── オンボーディングの
  途中、扉に着く前、あるいは通信が一度も通っていない iPhone ── のものは、
  サーバーに無いので履歴も無い。**上の消え方 6 は、この案では戻せません。**
- **iPhone の側が壊れている場合、サーバーを直すだけでは戻りません。**`syMerge()` は
  読めない側を捨てずに iPhone の側を返すので、サーバーに良い版を書き戻しても、
  次の同期でまた壊れた版が上がります。**上がってきたかどうかは、前の版を
  もう一度並べれば分かります**（戻した直後より新しい行が増えている）。
  **直すのはアプリ側の仕事で、この案の外です。**
- 投稿・下書き・写真・声（案B と C の領分）。
- サーバーに写しの無いもの ── 設定 20 欄、`wsys`、`recent`、テーマ、表示言語。
- **本人が消したもの。**言語の削除も、アカウントの削除も、この表の行を
  一緒に持っていきます（外部キーが cascade）。**意図してそうしています。**

### 案B ── 消える直前の行を、消えた置き場に写す

**何を、どこに、どれくらい**

`post` `draft` `language` `slice` の行が DELETE されるとき、BEFORE DELETE の
トリガで、その行を丸ごと jsonb にして一つの表に写します。

```
gone(表の名前, 行の id, 誰の, 中身 jsonb, いつ)
```

**アカウント削除は写しません。**`account_delete()` は `auth.users` を消し、
そこから全部カスケードします。オーナーの線 ──「アカウント削除は本当に全部
消える」── を守るため、この道だけはトリガを免除します。

期間で変わるところ:

- **短い** ── 「今日の午後に投稿が全部消えた」に答えられる。
- **長い** ── 「先週の下書きが無い」に答えられる。ただし、**消えた投稿の
  中身を長く持ち続けること自体が、人によっては嫌がられます。**これは
  技術ではなく、オーナーの決めることです。

**誰がどうやって戻すのか**

ダッシュボードの SQL で、`gone` から選んで元の表に insert し直します。
案A と同じく、`is_admin()` で守った関数を一つ用意すれば一行で呼べます。

**大きさ:** 中。**サーバー側の作業:** 要る。`npm run rls` も。

**この案で守れないもの**

- **バケツのバイト。**写真と声は行ではないので、行を戻しても
  `post-media` から消えたバイトは戻りません。投稿の削除は
  `netDropMine()` が先にバイトを消します。**戻るのは文と器だけで、
  写真の付いていた投稿は写真の無い投稿として戻ります。**
- アカウント削除で消えたもの（意図してそうしています）。
- iPhone の中だけで消えたもの。DELETE がサーバーに届いていない消え方 ──
  上の 2・3・4 ── には何も効きません。
- **上書きで消えたものには効きません。**これは案A の領分です。

### 案C ── データベース全体を、ある時点に戻せるようにする

**何を、どこに、どれくらい**

アプリもスキーマも一行も変えません。Supabase 側の設定です
（Point-in-Time Recovery、または定期的なダンプ）。**今どうなっているかは
未確認です** ── `supabase/setup.md` に一言も書かれていません。
PITR は Supabase の有料の段が要ります。**どの段を契約しているかも
確認していません。**オーナーがダッシュボードで見る所です。

期間で変わるところ: 巻き戻せる幅がそのまま期間です。短ければ「今日」だけ、
長ければ「先週」まで。費用も期間で変わります。

**誰がどうやって戻すのか**

オーナーがダッシュボードから。ただし**全体が一つの時点に戻ります。**
一人のために全員を巻き戻すことになるので、実際には別のインスタンスへ
復元して、そこから必要な行だけ取り出して書き戻す、という手順になります。
**一人を助けるには手間がかかる道です。**

**大きさ:** 小（設定だけ）。**サーバー側の作業:** 要る（ダッシュボード）。
コードの作業はゼロ。

**この案で守れないもの**

- **バケツ。**PITR はデータベースの話で、Storage は別です。写真と声は戻りません。
- **サーバーに写しの無いもの。**サーバーに無いものは、どの時点にも無い。
- **細かい復旧に向きません。**「この人のこの言語だけ」を戻すのに、
  全体の復元が要ります。
- 巻き戻す幅の外で起きたことは戻せません。
